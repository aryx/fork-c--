notes_arm64.txt
================

Written: 2026-08-25, against commit 8443865 (parent of the commit that adds
this file and the AArch64/macOS backend itself). All claims below are
VERIFIED: read in the code, or observed by actually running `qc -arm64 ...`
NATIVELY on this machine (no qemu, no cross toolchain - see "Toolchain"
below), not inferred from upstream Lua (there is no upstream to infer from
here - see "What this is").

What this is
------------
AArch64 is the eighth non-x86 backend plugged into this fork, after ppc,
sparc, alpha, mips, arm, riscv64, and riscv32. Like ARM32/RISC-V, upstream
qc-- has no AArch64 code at all (AArch64 postdates upstream qc--'s active
development), so this is new development with no .nw counterpart anywhere -
every file in arch/arm64/ is plain source with no syncweb (*s:*)/(*x:*)/
(*e:*) markers, and arch/arm64/Makefile's SRCNW is empty, same situation as
arch/arm/ and arch/riscv64/.

What makes this backend different from every other one in this fork: it
targets this development machine's OWN architecture (Apple Silicon,
arm64-apple-darwin). Every other backend needs a cross toolchain and/or
qemu to assemble, link, and run its output. This one just needs "clang" -
no -target override, no QC_AS/QC_LD, no -static (Apple does not support
static-linking libSystem at all), no emulator. It is also, for that same
reason, the only backend whose Mach-O output has actually been verified end
to end on Mach-O's own real hardware/linker - arch/ppc/ppcasm.ml's Mach-O
output has existed in this codebase for a long time but (per its own
driver/main.ml comment) could never be tested end to end, since no PowerPC
Mac exists to run it on.

Target shape (verified in arch/arm64/arm64.ml)
-----------------------------------------------
- 64-bit little-endian, Space.Standard64 (like riscv64.ml/alpha.ml, unlike
  arm.ml's Standard32). 31 general registers x0-x30 plus a stack pointer
  modeled as index 31 within the same 'r' space (unlike RISC-V, where sp is
  just an ordinary numbered register with an alias - AArch64 assembly has NO
  "x31" spelling for sp at all; the literal mnemonic "sp" must be used, so
  arm64rec.mlb's register printer special-cases index 31).
- Condition-code model, architecturally identical to ARM32 (a single flags
  pseudo-location - AArch64 kept ARM32's NZCV design, unlike RISC-V's
  register-vs-register branches): arm64_subcc sets `cc`, named condition
  operators (arm64_eq/arm64_ne/arm64_lt/arm64_le/arm64_gt/arm64_ge/
  arm64_ls/arm64_hi) consume it. arm.ml was the direct template for this
  half of Post; riscv64.ml was the template for everything 64-bit-width-
  related and the no-branch-delay-slot do_call/cut_to ordering (both
  arm.ml's and riscv64.ml's are the same "no delay slot" shape anyway).
- T.float = Float.ieee754 is declared (matching Metrics.default, so
  demos/hello_arm64.c-- needs no explicit float pragma - unlike arm.ml's
  Float.none, which forced demos/hello_arm.c-- to add one), even though
  Post.unrm/binrm/dblop are still Impossible.unimp/Unsupported - same
  deferral riscv64.ml's own T.float makes.
- T.memory = [64] only, NOT [8;16;32;64] the way every other integer
  backend here declares. AArch64's sub-word load/store forms (ldrb/ldrh/
  ldrsb/ldrsh/ldrsw) need a W-register-vs-X-register distinction (a 32-bit
  register write implicitly zero-extends into the corresponding 64-bit
  register - "ldrb w0, [...]" not "ldrb x0, [...]") that this pass did not
  verify empirically, so arm64rec.mlb has no grammar rules for them at all
  and the capability is not declared. Not reachable by demos/hello_arm64.c--
  (its only memory access is the string literal, addressed as a pointer,
  never loaded byte-by-byte at the C-- IR level - printf does that in C).
  A real gap for future programs; see "Known remaining gaps" below.

Immediate materialization: NOT "ldr rX, =imm"
-------------------------------------------------
armrec.mlb's "ldr rX, =imm" trick (a GNU-as pseudo-op that builds a literal
pool + PC-relative load) does NOT carry over to the 64-bit register form on
Apple's LLVM-based integrated assembler - empirically confirmed broken:

    ldr x0, =0x123456789

assembled with no error, but `otool -tv` on the resulting object showed it
reserved only 4 bytes in the literal pool (a ".long", not a ".quad") for
what should be an 8-byte load, silently truncating the high byte and then
reading the next instruction's own encoding as high-order garbage. This is
specific to the 64-bit register form on THIS assembler - not investigated
whether GNU binutils' aarch64-linux-gnu-as gets it right, since this
backend has no ELF sibling to test that against yet (see "Not attempted").

Fixed by not using it at all: arm64rec.mlb's `li64` instead builds a movz +
up to three movk instructions explicitly (movz sets the first non-zero
16-bit chunk, or #0 if the whole value is zero; each subsequent non-zero
chunk folds in via movk, which does not disturb the other bits). Always
correct, needs no assembler pseudo-op cooperation, and would work
identically against GNU as if an ELF sibling is ever added. Costs up to 4
instructions per immediate where "ldr rX, =imm" would have cost 1 (plus a
literal-pool entry) - a real code-size/speed tradeoff against arm.ml's own
approach, not revisited here since demos/hello_arm64.c--'s immediates are
all small (single movz suffices for all of them in practice).

No native 12-bit add/sub-immediate encoding is used either, even though
AArch64 has one (unlike ARM32's fully-rotated 8-bit encoding, which really
does need the ldr-pseudo-op fallback for most values) - every arithmetic
immediate goes through the same li64 + x16-scratch materialization,
matching armrec.mlb's original "always materialize, no direct-encode fast
path" simplicity. Worth revisiting once real programs (not just
demos/hello_arm64.c--) exercise this backend - see "Not attempted".

Register roles (verified in arm64cc.ml/arm64call.ml)
------------------------------------------------------
AAPCS64 crossed with Apple's own platform-ABI addendum where it is
stricter:
  x0-x7     argument/return registers, volatile (results use only x0 -
              no struct-return/multi-value-return support yet)
  x8        indirect-result register, volatile (not modeled - no struct
              return)
  x9-x15    volatile temporaries
  x16/x17   IP0/IP1 - x16 reserved as this backend's own scratch register
              (arm64rec.mlb's li64/immediate-materialization rules
              unconditionally clobber it), NOT in vol_int/nvl_int - same
              reservation class as arm.ml's r12/ip, riscv64.ml's x5/t0.
              x17 also excluded, unused but reserved defensively (linker
              veneers may clobber it).
  x18       reserved - Apple's platform register. MUST NOT be used by any
              code on Apple platforms (verified: this is a hard Apple ABI
              rule, unlike plain AAPCS64/Linux where x18 is sometimes
              available) - excluded from every pool.
  x19-x28   non-volatile (callee-saved) - the allocatable nvl_int pool.
  x29/fp    reserved, NOT in nvl_int - same frame-pointer-chain reservation
              class as arm.ml's r11/riscv64.ml's x8/s0, if anything
              stricter here: Apple's own unwinder/crash reporter relies on
              a valid frame-record chain, not just fork-tiger's gc.c (as on
              ARM32/RISC-V) - not yet verified whether this backend
              actually maintains a conventional stp/ldp frame record (see
              "Not attempted" - the generated code today does NOT emit one;
              it manages its own stack layout via qc--'s own Call.t/
              Framelayout machinery, same as every other backend here, none
              of which construct a standard frame-pointer chain either).
  x30/lr    return address, handled specially (arm64call.ml's ra/
              ra_on_entry/ra_on_exit), not a general allocatable register.
  sp        stack pointer, 16-byte aligned always - Apple enforces this in
              hardware (a misaligned SP faults), stricter than plain
              AAPCS64's "only at public interfaces". Arm64call.ml's
              sp_align = 16 (vs. ARM32's 8) - verified in the one real test
              this pass ran: the generated hello_arm64 prologue/epilogue
              both allocate/deallocate exactly 16 bytes via "add sp, sp,
              x16" with x16 materialized to -16/16, and it ran correctly
              on real hardware without a SP-alignment fault.

Toolchain
---------
Just "clang" (driver/main.ml's default_arm64_cc), no -target override:
this machine IS arm64-apple-darwin25.6.0 (confirmed via `uname -a`/`clang
-dumpmachine`), so clang's default target already matches. No QC_AS/QC_LD
override needed in demos/Makefile's arm64 rule (every other backend's rule
sets both). No -static: Apple's ld64 refuses to statically link against
libSystem at all (unlike every Linux-hosted backend here, which all pass
-static). No qemu: the binary runs directly.

Bugs found and fixed while bringing this up
---------------------------------------------
- ld64 ("pointer not aligned in 'anon-13'") rejected the generated object
  at LINK time (not assembly time) - it infers each Mach-O section's
  alignment from what is actually emitted at its start, and refuses to
  place an 8-byte pointer relocation (every ".quad symbol" this backend's
  own `addr` method and the shared pcmap-emission code produce) into a
  section whose inferred alignment is 1. Hit against demos/hello_arm64.c--'s
  own pcmap section, which - like every other backend's generic pcmap
  emission - opens with a bare ".quad" and no preceding ".align". This is
  Mach-O/ld64-specific: none of the ELF-targeting backends here have ever
  hit it, since their linkers don't do this alignment inference the same
  way. Fixed generically in arm64asm.ml's `section` method: every non-text
  (__DATA) section now gets an unconditional ".align 3" (8 bytes)
  immediately after its ".section __DATA,%s" directive - safe and never
  wasteful, since every value this backend ever emits is .byte or .quad
  (T.memory = [64], see above).
- Confirmed (NOT a bug, but worth recording since it contradicts
  arch/ppc/ppcasm.ml's own untested assumption): ppcasm.ml's generic
  ".section __DATA,%s" pattern (using the qc---internal section name like
  "data"/"pcmap"/"pcmap_data" literally as the Mach-O section name, not the
  conventional "__data" double-underscore form) DOES assemble and link
  correctly on this machine's real toolchain - hand-verified with a
  standalone test .s before writing arm64asm.ml (`.section __DATA,data`,
  `.section __DATA,pcmap` both linked and ran fine). Reused unchanged from
  ppcasm.ml. Likewise ".align n" taking a log2 exponent (not a byte count)
  was hand-verified with `otool -s` against a test object before trusting
  ppcasm.ml's own `align` method's log2 computation.
- Confirmed (also not a backend bug, a toolchain fact worth recording): a
  plain "bl _printf"/"bl _foo" referencing a libSystem symbol assembles AND
  links correctly with no PIC-stub machinery at all (no
  .indirect_symbol/.lazy_symbol_pointer/.picsymbol_stub, the dance
  ppcasm.ml's own `import` method does for the classic 32-bit Mach-O PIC
  ABI) - ld64 synthesizes whatever stub islands an arm64 call actually
  needs. arm64asm.ml's `import` is therefore trivial (`this#new_symbol s`),
  matching riscv64asm.ml's/x86asm.ml's own shape, not ppcasm.ml's.

Known remaining gaps
---------------------
- Sub-word memory access (T.memory = [64] only) - see "Target shape" above
  for exactly why (W-register-vs-X-register correctness risk, not
  verified). The next real program this backend is pointed at will very
  likely need this.
- No float support at all (same deferral every other new-development
  backend here makes on its first pass).
- No native AArch64 add/sub 12-bit-immediate encoding (always materializes
  through movz/movk + x16 instead) - correct but larger/slower code than
  necessary; a real backend would want a guarded direct-encode rule the way
  a fits_imm12-style check could add.
- Whether this backend maintains a conventional Apple-ABI frame-pointer
  chain (stp x29,x30 at entry / ldp at exit) has NOT been verified either
  way - the generated hello_arm64 code does not appear to (it manages RA
  via arm64call.ml's ra_on_entry/where_to_save_ra/ra_on_exit hooks onto
  qc--'s own stack layout, same as every other backend), which may or may
  not matter until something needs Apple's own unwinder (crash reporter,
  Instruments, lldb backtraces) to walk through this backend's frames.
- -O3 not tried against this backend at all yet (every other new-
  development backend here hits a known, shared, cross-backend -O3 hang -
  see notes_arm.txt's/notes_riscv.txt's own "Known remaining gaps" - very
  likely the same story here, not re-diagnosed).
- Tiger test suite (tests/tiger/) not attempted yet - this session stopped
  at the hello.c-- milestone per explicit scope (the user asked for
  hello.c-- first, tiger64 later - see also notes_64bits.txt, whose
  Cmm_Word/pcmap-width fix already generalizes to this backend for free
  since it targets every 64-bit backend, not just riscv64).
- No Linux/ELF sibling ("-arm64-elf" or similar) - macOS/Mach-O only, per
  the user's explicit "for now macOS" scope. Would follow arch/ppc/
  ppcelfasm.ml's precedent: same arm64.ml/arm64rec.mlb, a second
  Asm.assembler class.

pcmap.ld has no Mach-O equivalent - fixed via ld64's own symbol synthesis
------------------------------------------------------------------------------
Every ELF-hosted backend here links against runtime/pcmap.ld, a GNU-ld
"-T" linker-script fragment that places every input object's ".pcmap"
section together and defines two symbols (Cmm_pc_map, Cmm_pc_map_limit)
marking its start/end - pcmap.c's own GC-metadata-table walk (bsearch over
Cmm_pc_map..Cmm_pc_map_limit) depends on these. Mach-O's ld64 has NO
linker-script mechanism at all (no "-T", nothing equivalent) - this would
otherwise have been a hard blocker.

Fix: ld64 already auto-synthesizes a "section$start$SEGMENT$section"/
"section$end$SEGMENT$section" symbol pair for ANY section, no script
needed - a well-known but under-documented Mach-O linker feature (used
e.g. by Objective-C runtime/Swift metadata section registries for exactly
this "declare a custom section, find its bounds at runtime" pattern).
Empirically verified BEFORE touching pcmap.c, with a standalone hand-
assembled test .s (a `.section __DATA,pcmap` with three .quad entries) and
a small test .c declaring
`extern long Cmm_pc_map[] __asm("section$start$__DATA$pcmap");` - printed
the correct count and values. runtime/pcmap.c's own two extern
declarations are now `#ifdef __APPLE__`-guarded to use this form (see that
file's own "claude:" comment); no pcmap.ld counterpart exists or is needed
for Mach-O at all - the #ifdef is the whole fix. arm64asm.ml already
emitted the section as plain ".section __DATA,pcmap" (no ELF ALLOC-flag
dance needed, per the first pass's own findings), so the segment/section
names the __asm strings reference were already exactly right.

NUM_REGS/FP_REG for __aarch64__ - computed with a throwaway verification harness, not hand-derived
------------------------------------------------------------------------------------------------------
qc--runtime.h's NUM_REGS and gcc-linux.c's FP_REG (the flat register-index
qc--'s own Target.mk_reg_ix_map numbering assigns to x29/fp - needed so
Cmm_init_c_frame can find the C caller's frame-pointer chain by reading
`a->regs[FP_REG]`) both needed a new #ifdef __aarch64__ branch. Every
existing backend's own NUM_REGS comment describes its breakdown as if
space_to_regs generates exactly `count` registers per space (e.g. "c(6)-
>0-5" for a `SS.c 6 ...` declaration) - but Target.mk_reg_ix_map's
space_to_regs helper (target/target.ml) actually generates `count+1`
registers per space (0..count inclusive, an off-by-one over-generation,
apparently harmless everywhere else only because NUM_REGS is always
declared with generous slack over the naive sum). Rather than propagate
that same imprecision, this pass wrote a throwaway OCaml harness (a
scratch dune executable, deleted after use - not committed) that calls the
REAL Target.mk_reg_ix_map on arm64.ml's actual T.spaces and looks up the
integer index for x0/x28/x29/x30/sp directly. Confirmed result: x0->37,
x28->65, x29(fp)->66, x30(lr)->67, sp(x31)->68, total=70 (c: 4 slots
0-3, f: 33 slots 4-36, r: 33 slots 37-69). NUM_REGS set to 96 (generous
margin over 70, matching riscv64/alpha/mips's own 96); FP_REG set to the
confirmed 66. Both comments in qc--runtime.h/gcc-linux.c cross-reference
this harness and its result, in case a future NUM_REGS discrepancy needs
re-deriving for another target.

Confirmed portable, contrary to its own filename: runtime.c/pcmap.c/gcc-linux.c
------------------------------------------------------------------------------------
Despite "gcc-linux.c"'s name, grepping runtime/runtime.c, pcmap.c, and
gcc-linux.c turned up no Linux-specific headers or syscalls at all - only
<assert.h>/<stdio.h>/<stdlib.h>/<stdarg.h>/<string.h>, all portable. The
name is about "interoperating with gcc-compiled C code's frame-pointer
convention," not about the Linux platform specifically. Confirmed by
building all three with plain clang on this host with zero portability
fixes needed beyond the NUM_REGS/FP_REG/pcmap branches above (which are
architecture-, not OS-, specific - the FP_REG *value* is identical between
Linux-gcc and Darwin-clang since both follow the same AAPCS64 x29 frame-
record convention under -fno-omit-frame-pointer).

Modified files (arch/arm64/, widening operator/memory coverage)
-------------------------------------------------------------------
- arch/arm64/arm64rec.mlb - added %lobits support (Post.lostore's only
  producer - a free no-op onto a narrower-width memory *store*, same
  reasoning as every sibling backend's identical "lobits" exp case) and
  three new grammar rules for narrow (8/16/32-bit) stores (strb/strh/str
  with a W-register source operand - AArch64 has no "strb x0,..." form at
  all, only "strb w0,..."; a new `wreg`/`wregl`/`wreg32` nonterminal chain
  materializes the W-register spelling of the same physical register,
  alongside the existing X-register `reg`/`regl`). Unblocked
  tests/tiger64/stdlibcmm.c--'s compile (fork-tiger's I/O buffer code does
  plain byte stores) - the FIRST real compile-time error this backend hit
  past demos/hello_arm64.c--'s own coverage ("unknown operator lobits").
  Narrow *loads* (sign/zero-extending sx/zx from memory) remain
  unimplemented - confirmed this is not new-to-arm64: arm64rec.mlb's `exp`
  function (like armrec.mlb's/riscv64rec.mlb's own) has no case for the
  "sx"/"zx" operators at all, so their own Sx/Zx-shaped grammar rules were
  ALREADY dead code before this backend existed too (notes_arm.txt already
  flags this exact gap for ARM32) - not something this pass introduced or
  was in scope to fix, and not hit by tests/tiger64/'s 5 passing tests.
- arch/arm64/arm64.ml - T.memory widened from [64] to [8;16;32;64]
  (matching every sibling backend's own declaration - the sx/zx-load gap
  above means this is somewhat aspirational for loads, but real and
  exercised for stores); three new "lobits" capability entries
  ([wordsize;8]/[wordsize;16]/[wordsize;32], mirroring arm.ml's/
  riscv64.ml's own).
