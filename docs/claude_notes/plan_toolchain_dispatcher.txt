plan_toolchain_dispatcher.txt — turn qc--'s already-detected cross
toolchains into a queryable/dispatchable interface, so client languages
(fork-tiger) stop re-deriving the same detection logic in their own
configure scripts.
Written 2026-09-01, against commit 7387646. Re-synced 2026-09-02 against
commit 665b1d2 — `driver/main.ml` had, in the meantime, been split into
`driver/CLI.ml` (the actual logic)/`CLI.mli`/`Main.ml` (a two-line entry
point), and a `-m68k` backend was added; every `driver/main.ml:N`
reference below has been corrected to `driver/CLI.ml:N`. A first slice
(`-print-cc`) is now implemented — see "Implemented so far" below.

Prompted by: fork-tiger's `configure` has its own `detect_backend` function
that duplicates this repo's `configure` `detect_backend` almost line for
line (same toolchain package names, same apt-get hints, same
native-uname-m patterns) just to know, per backend, which cross-compiler/
archiver/qemu-user binary to use for building fork-tiger's own runtime/
stdlib C and C-- sources. Considered (and rejected) making qc-- compile C
itself; landed on: qc-- becomes a thin *dispatcher* over toolchains it
already locates, not a Zig-cc-style bundled toolchain manager (no bundled
clang/libc/crt objects — out of scope, much bigger effort, not the goal
here).

Verified: current state
------------------------------------------------------------------
- `configure`'s `detect_backend` (called once per backend: ppc-elf, sparc,
  alpha, mips, arm, riscv32, riscv64, arm64, amd64, plus the always-on x86
  block and the Darwin-only arm64-mach-o/amd64-mach-o block) is the single
  source of truth for CC_<ARCH>/AR_<ARCH>/RUN_<ARCH> — package hints,
  qemu-user binary names, and native-arch detection all live here.
- This is written to `Makefile.config`, read only by shell Makefiles/test
  scripts (`tests/run-tiger-<arch>.sh` etc.) in *this* repo.
- `Makefile.config`'s CC_<ARCH>/AR_<ARCH>/RUN_<ARCH> is invisible to the
  `qc` binary itself — that part of the original write-up still holds.
  `driver/this.ml`/`this.in` (an `@this@`-substitution template) still
  look like leftover mk(1)-era machinery, not currently wired into the
  dune build, not a precedent worth reusing.
- No `QCLIB` concept exists in this repo at all — it's a fork-tiger-side
  convention (fork-tiger's own `configure` derives it from `qc`'s install
  location, `driver/dune`'s comment confirms: `dune install` puts the
  run-time under `<prefix>/lib/cmm/`, which is exactly what fork-tiger's
  `configure:184` calls `QCLIB`). So there is no stable, install-time
  location where this repo *itself* consumes anything back — but the
  pattern (an installed `<prefix>/lib/cmm/` dir) exists and could host a
  file, if one turns out to be needed (see AR/RUN below).
- Existing flag convention (`driver/CLI.ml:1004-1043`, was
  `driver/main.ml:961-1049` before the CLI.ml split): single-dash,
  **one flag per backend** (`-x86`, `-ppc-elf`, `-arm64`, `-arm64-mach-o`,
  `-amd64`, `-amd64-mach-o`, `-riscv32`, `-riscv64`, `-arm`, `-m68k`,
  `-mips`, `-sparc`, `-alpha`), not a generic `-arch <name>` parameter —
  this matters because it already disambiguates cases a plain arch string
  wouldn't (arm64 ELF vs Mach-O are separate flags).
- **Major finding, changes the design below**: `-as <cmd>`/`-ld <cmd>`
  are not just override flags with no default — `driver/CLI.ml:558-577`
  (`effective_cc`) already resolves an *unset* `-as`/`-ld`/`QC_AS`/`QC_LD`
  to a per-backend default (`default_i386_cc`, `default_arm64_cc`, ...,
  `driver/CLI.ml:229-345`), used when qc-- assembles/links its *own*
  emitted C-- output. This table is more authoritative than anything a
  fresh `detect_backend`-style re-derivation would produce: it already
  encodes real per-backend nuance (clang-with-`-target` preferred over a
  GNU cross-gcc where clang cross-assembles fine but has no real sysroot
  for full static linking, e.g. `-sparc`/`-mips`; a hard `failwith` where
  no default is safe at all, e.g. `-alpha`, forcing an explicit
  `-as`/`-ld`/`QC_AS`/`QC_LD`). It only covers the compile/link *command*
  though — there is no equivalent table for an archiver or a qemu-user
  runner (qc-- itself never builds a `.a` or runs a test binary), so
  AR_<ARCH>/RUN_<ARCH> genuinely have no existing counterpart to expose
  and would still need fresh detection logic if qc-- is to answer for
  them too.
- Also relevant to fork-tiger's own CC_<ARCH> choice, not just qc--'s own
  `-as`/`-ld`: checked fork-tiger's `demos/Makefile` directly (`:150-166`
  for x86, `:456` for arm64) — fork-tiger never actually uses qc--'s own
  `-ld` at all. The pattern is `$(QC) -globals -stop .o -o $@ $<`
  (compile+assemble a `.c--` to `.o`, via qc--'s own `-as` default) then
  `$(CC_ARM64) -static $(TOP)/runtime/.../runtime.o $< ... -o $@` (link
  directly, via fork-tiger's *own* CC_<ARCH>, bypassing qc-- entirely for
  the link step) — true for every backend, not just x86. So the real
  compatibility requirement is narrower than first thought: fork-tiger's
  CC_<ARCH> needs to be object-format/ABI-compatible with whatever qc--'s
  `-as` (not `-ld`) used to assemble that backend's `.c--` output — which
  is why the implemented `-print-cc` below reads `as_cmd`, not `ld_cmd`
  (they share the same default table per backend, so this only matters
  when `QC_AS`/`QC_LD` diverge, but `-as`'s resolution is the
  conceptually correct one to expose here).

Alternatives considered
------------------------------------------------------------------
- qc-- compiles fork-tiger's C sources (runtime.c, alloc.c, etc.) itself,
  becoming the one place cross-compilation happens. Rejected: qc-- compiles
  C--, not C — fork-tiger's runtime/stdlib C files are a fork-tiger-side
  concern qc-- has no reason to own; doing this would turn qc-- into a
  general C-toolchain manager just to solve fork-tiger's duplication.
- Full Zig-cc-style toolchain manager: bundle clang plus libc headers/crt
  objects per target so no system cross-toolchain install is needed at
  all. Rejected for now as much bigger in scope than the actual problem
  (fork-tiger's `configure` re-deriving detection qc-- already does) and
  explicitly not this plan's goal — qc-- stays a *dispatcher* over
  whatever cross-toolchains are already on the host, same assumption
  `detect_backend` already makes today.
- Client repos source a shell fragment / this repo's raw `Makefile.config`
  directly, instead of going through the `qc` binary. Considered as a
  lighter first cut; superseded by the `-print-*` design because it keeps
  the contract at `qc`'s CLI (discoverable via `-help`, works from an
  install prefix without the client needing to know this repo's
  build-tree layout) rather than a second ad hoc file format another
  repo's `configure` has to locate and parse.
- Generic `-arch <name>` parameter (e.g. `qc -arch arm64 -print-cc`, or
  `qc -print-cc=arm64`) instead of reusing the existing per-backend
  boolean flags. Rejected: the per-backend flags already exist and already
  disambiguate cases a plain arch string doesn't (`-arm64` vs
  `-arm64-mach-o` are separate flags, not one arch name plus a second flag
  to pick ELF vs Mach-O), and matches this file's own established
  convention (`-x86`, `-ppc-elf`, ... one flag per backend) instead of
  introducing a second, parallel arch-naming scheme alongside it.

Correction (2026-09-02, same day): `-print-cc` reusing `default_*_cc`
was wrong
------------------------------------------------------------------
The 09-01-evening "Proposed design" above shipped `-print-cc` reading
`effective_cc`'s existing `default_*_cc` fallback table directly, on the
theory that it was already-vetted, authoritative data. It is not:
`default_i386_cc = "clang -target i386-unknown-linux-gnu"` is a hardcoded
guess baked into `driver/CLI.ml` at whatever host the person who wrote
that line happened to be using, never verified against *this* host.
Caught by hand-testing `qc -x86 -print-cc` and trying to actually use its
output: on this repo's own aarch64-linux dev host,
`clang -target i386-unknown-linux-gnu -static t.c -o t` fails outright
(`/usr/bin/ld: unrecognised emulation mode: elf_i386` — no i386 sysroot/
linker support here), while `configure`'s own `detect_backend`-found
`i686-linux-gnu-gcc` links the same program fine. So qc--'s own
`default_*_cc` table is not a reliable stand-in for "the toolchain that
actually works on this machine" — `configure`'s real, host-run
`command -v`-based detection is, and always was, the only trustworthy
source; the mistake was assuming a static compiled-in guess could
substitute for it.

Fix: `configure` now also generates `driver/Config.ml` (gitignored, like
`Makefile.config` — the user's call: no checked-in fallback, `dune
build`/`make` requires `./configure` to have run first, same as
`Makefile.config` already requires for the test scripts) — one
`let cc_<backend> : string option = Some "..." | None` per backend, from
the very same `detect_backend` values that go into `Makefile.config`.
`effective_cc` (`driver/CLI.ml`) now resolves in this order: explicit
`-as`/`-ld`/`QC_AS`/`QC_LD` (unchanged) > `Config.cc_<backend>` if
`Some` > the old `default_*_cc` guess as a last resort (kept only for
`Config.ml`'s own `None` case, i.e. a backend `detect_backend` didn't
find anything for, or `dune build` run without `./configure` at all).
This also fixes qc--'s own `-x86 -as`/`-ld` default on hosts like this
one, not just `-print-cc` — a real bug, not just a naming/plumbing
detail.

Chosen deliberately over the alternative (an install-time
`toolchains.conf` read at `qc` runtime, from the very first 09-01
write-up): baking real detection in at `./configure` time, compiled into
the `qc` binary via `driver/Config.ml`, needs no runtime file-lookup/
install-prefix logic at all, and matches this repo's own existing
`this.in`/`this.ml` precedent (a `.ml` regenerated by the build, not
looked up at runtime). Trade-off, explicitly accepted (user: "so this is
done at configure time once and for all"): a toolchain installed *after*
`./configure` last ran won't be picked up until it's re-run — same
staleness `Makefile.config` already has today, not a new kind of
staleness for this codebase, and cheaper than an exec + `command -v` on
every single `qc` invocation.

Proposed design (updated)
------------------------------------------------------------------
1. `configure`: `detect_backend` logic unchanged. Now additionally
   writes `driver/Config.ml` (gitignored) right after `Makefile.config` —
   **done**, see below.

2. `qc -<arch> -print-cc` (**implemented**, see below): `effective_cc`'s
   new resolution order (above). A client `configure` captures it with
   e.g. `CC_ARM64=$(qc -arm64 -print-cc)`.

3. AR_<ARCH>/RUN_<ARCH> — not implemented, still not a simple query flag
   since qc-- has no existing per-backend archiver/qemu-user table to
   expose (qc-- itself never builds a `.a` or runs a test binary), unlike
   CC which now does via `Config.ml`. Two options, not yet chosen:
   (a) extend `Config.ml`/`configure` with `ar_<backend>`/`run_<backend>`
       too (real new code: `detect_backend` already finds `RUN_<ARCH>`,
       just needs to flow into `Config.ml` the same way CC now does; the
       archiver is almost always plain `ar` everywhere, so may not even
       need detecting) - or
   (b) leave AR_<ARCH>/RUN_<ARCH> to fork-tiger's own `configure` as
       before and only ever ask qc-- for CC_<ARCH>.
   (a) got a lot cheaper now that the `Config.ml` plumbing exists for CC
   — leaning towards it now, opposite of the 09-01 lean towards (b).

4. `qc -available-archs`: not implemented. With `Config.ml` in place this
   is now simpler than originally scoped — just report which
   `Config.cc_<backend>` are `Some` (no live `command -v` probing needed
   at `qc` runtime, `configure` already did that once).

5. fork-tiger's `configure`: not yet started. Replace the CC_<ARCH> half
   of its own `detect_backend` (currently ~configure:257-380, see
   fork-tiger's own CLAUDE.md "Other qc-- backends" section) with a call
   to `qc -<arch> -print-cc`, catching the `-alpha`-style failure case
   (still possible if fork-tiger's own `./configure` runs on a host where
   qc--'s `./configure` found nothing for that backend either) as "no
   default, fall back to fork-tiger's own detection or require an
   explicit override". AR_<ARCH>/RUN_<ARCH> detection stays as today
   pending the (a)/(b) decision above. `stdlib/Makefile`,
   `runtime/Makefile`, `tests/run-tests.sh` are untouched either way.

Future consideration: goken as an alternate toolchain family
------------------------------------------------------------------
Raised mid-plan: the user may, at some point, want CC_<ARCH> (the compiler
used for fork-tiger's own hand-written runtime/stdlib C files, and by
extension AR_<ARCH>/RUN_<ARCH>) to be able to point at `~/goken`
(goken9cc, at commit 2aa40ce25 as of this writing) instead of a GNU cross
toolchain — as an *additional option*, not a replacement for GNU/clang.
Checked `~/goken` to see what this implies for the design above:

- goken is a self-hosted Plan 9-lineage toolchain (per-arch compiler/
  assembler/linker triples: `8c`/`8a`/`8l` for x86, `6c`/`6a`/`6l` for
  amd64, `7c`/`7a`/`7l` for arm64, `vc`/`va`/`vl` for mips,
  `ic`/`ia`/`il` for riscv64, etc. — single-letter arch codes, not GNU
  triples), with its own object-file convention (`.5`/`.6`/`.7`/`.8`/...
  extensions, not `.o`) and its own archiver (`compilers/.../ar` in
  `lib_toolchain/`). Raw `Xc`/`Xa`/`Xl` do not share gcc's CLI (separate
  compile/assemble/link steps, different flags) or a unified driver.
- `compilers/pcc/pcc.c` (goken's "portable wrapper", built for Plan 9 APE)
  *is* a gcc-workalike front end — takes `-c`/`-o`, shells out to `gcc -E`
  for preprocessing, then drives the right per-arch `Xc`/`Xa`/`Xl` steps
  itself. This looks like the right integration point for CC_<ARCH>: `qc
  -<arch> -print-cc` resolving to something like `~/goken/bin/pcc` (with
  whatever arch-selection env/flag goken's own build uses) keeps
  CC_<ARCH> gcc-flag-shaped regardless of which family backs it, which is
  what fork-tiger's Makefiles already assume — not verified end to end
  (haven't test-compiled fork-tiger's runtime.c through pcc), just
  plausible from pcc.c's flag handling.
- Consequence for the design above, corrected now that the mechanism is
  known to be `effective_cc`/`default_*_cc` (`driver/CLI.ml:229-345,558-
  577`), not `configure`'s `detect_backend`: `effective_cc` would need a
  family choice per backend (GNU cross / clang / goken), not just one
  hardcoded `default_<arch>_cc` string — closer to how the
  arm64-mach-o/amd64-mach-o pair already branches gnu-cross vs clang by
  host today, just as a selectable option instead of a host-conditional.
  A new flag/env var (`-cc-family=gnu|clang|goken`, or `QC_CC_FAMILY`)
  picking which `default_*_cc` variant `effective_cc` falls back to seems
  the natural extension - `-print-cc` then just reflects whichever family
  was selected, no separate design needed for the query side.
- Explicitly out of scope for this design and NOT resolved here: whether
  a goken-produced `.o` can actually be linked together with what qc--
  itself assembles (confirmed 09-02: fork-tiger links via CC_<ARCH>
  directly, against `-as`'s output specifically - see the corrected
  finding above - so this is precisely the compatibility a goken
  CC_<ARCH> would need to satisfy against whichever family `-as`
  resolves to for that backend). qc--'s own `-as`/`-ld` default is
  GNU-binutils/clang-syntax-bound today; a goken family option would sit
  alongside it in `effective_cc`, per the corrected consequence above,
  not replace it - so this reduces to "does a goken-produced `.o` link
  against a clang/gcc-produced `.o` for the same arch/ABI", still not
  investigated.

AR/RUN: centralized in qc-- after all (2026-09-02, same day)
------------------------------------------------------------------
The "Open questions" AR/RUN (a)-vs-(b) fork above is resolved: user
"tiger should not do any toolchain detection on its own; it should rely
on what was done by qc. same for AR" - then, prompted about `-print-run`
specifically: "to avoid again repeating the same thing in both qc and
tiger and possible other c-- frontend". So (a): qc-- now answers for
CC, AR, and RUN, not just CC - fork-tiger's `configure` should end up
doing zero toolchain detection of its own once it switches over (not
done yet - still the last remaining step).

- **`-print-ar`** needed no new detection at all: a cross gcc is always
  `<triple>-gcc` with matching binutils `<triple>-ar` (the same trick
  fork-tiger's own `configure` already used for `AR32`/`AR_<ARCH>` -
  `configure:210-221`/`:250-251` there). `ar_of_cc` (`driver/CLI.ml`,
  right before `compile_file`) derives it from whatever `-print-cc`
  already resolved to (first word only, to handle multi-word cc's like
  `-sparc`'s `"sparc64-linux-gnu-gcc -m32"`), falling back to plain
  `"ar"` for anything not `<triple>-gcc` (the two Mach-O `clang`
  defaults). No `-ar`/`QC_AR` override was added to parallel `-as`/
  `QC_AS` - qc-- itself never builds an archive, so there is nothing
  internal for such an override to affect; a client that wants a
  different `ar` just ignores `-print-ar`'s output and uses its own.
- **`-print-run`** needed real new detection to flow through:
  `detect_backend` already finds `RUN_<ARCH>` (for qc--'s own
  `tests/run-tiger-<arch>.sh`), so `configure` now also writes
  `run_<backend>` into `Config.ml`, alongside `cc_<backend>`. Unlike CC,
  a plain `string option` would have been wrong here: `RUN_<ARCH>` has
  three real states from `detect_backend` - truly empty (native, no
  wrapper), a real `qemu-*` path (cross), or `NONE` (non-native, no
  emulator found) - and collapsing "native" and "not found" into the
  same `None` would have made `-print-run` unable to fail loudly on the
  second one, same "don't guess" principle as `require_cc`'s. So
  `Config.ml` now also carries `type run = Run_native | Run_via of
  string | Run_unavailable`, written by a new `ocaml_run` (next to
  `ocaml_opt`). `-print-run` prints nothing on `Run_native` (a client
  just runs the binary directly), the wrapper command on `Run_via`, and
  fails on `Run_unavailable`. The two Mach-O backends aren't probed by
  `./configure` at all but are still `Run_native` in `-print-run`'s own
  match (Rosetta 2 is OS-transparent - `amd64-mach-o`'s binaries run via
  plain `./a.out` same as any native one, no wrapper command exists to
  print).
- **Real bug found and fixed along the way**: `ocaml_opt` (the CC/
  `Config.ml` writer from the first `-print-cc` round) only checked
  `[ -n "$1" ]` (non-empty), not `detect_backend`'s own `NONE` sentinel
  for "not found" - so a backend `./configure` failed to find a
  toolchain for would have produced `Some "NONE"` in `Config.ml`,
  `effective_cc` would have returned the literal string `"NONE"` as if
  it were a real command, and `-print-cc`/`-as`/`-ld` would all have
  failed with a confusing `sh: NONE: command not found` instead of
  `require_cc`'s clear message. Latent until now because every backend
  happened to be found on this dev host in every `./configure` run so
  far - never actually exercised the `NONE` path. Fixed by teaching
  `ocaml_opt` (and the new `ocaml_run`) to treat literal `"NONE"` as
  "not detected" too.
- Verified by hand: `qc -arm64 -print-ar` -> `aarch64-linux-gnu-ar`;
  `qc -sparc -print-ar` -> `sparc64-linux-gnu-ar` (multi-word cc handled
  correctly); `qc -amd64-mach-o -print-ar` -> `ar` (clang fallback);
  `qc -arm64 -print-run` -> nothing, exit 0 (native on this host);
  `qc -amd64 -print-run` -> `/usr/bin/qemu-x86_64`; `qc -amd64-mach-o
  -print-run` -> nothing, exit 0; `qc -ppc-mach-o -print-run` -> fails,
  exit 2, clear message. `tests/run-compile.sh` still matches baseline
  after all of this.
