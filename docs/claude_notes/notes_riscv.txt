notes_riscv.txt
================

Written: 2026-08-17, against commit ed8a0ca (the ARM tiger-suite follow-up,
parent of the commit that adds this file and the RISC-V backends
themselves), updated the same day once tests/run-tiger-riscv32.sh reached
15/15 (see "RV32 tiger-suite bring-up" below - the biggest addition after

What this is
------------
RISC-V is the sixth and seventh non-x86 backends plugged into this fork,
after ppc, sparc, alpha, mips, and arm - two backends, not one, because
RISC-V comes in two widths this fork supports: RV64 (arch/riscv64/) and
RV32 (arch/riscv32/). Like ARM, upstream qc-- never had any RISC-V code at
all (RISC-V postdates upstream qc--'s active development), so both
backends are new development with no .nw counterpart anywhere upstream -
every file below is plain source with no syncweb (*s:*)/(*x:*)/(*e:*)
markers, same situation notes_arm.txt documents for arch/arm/.

Architecturally RISC-V is closer to MIPS than to ARM/SPARC/Alpha: it has NO
condition-code register at all - beq/bne/blt/bge/bltu/bgeu (plus GNU as's
ble/bgt/bleu/bgtu pseudo-ops) compare two registers directly and branch,
exactly the shape mips.ml's Post.bc_guard/bc_of_guard already model (unlike
ARM's/SPARC's/Alpha's own single-flags-register or compare-to-zero
designs). Where RISC-V differs from MIPS: it has no branch-delay slot (like
ARM/Alpha/PPC), so do_call/cut_to follow arm.ml's ordering discipline (sp
update before the jump that leaves control, not "in the delay slot" after
it) rather than mips.ml's. So both riscv64.ml and riscv32.ml are mips.ml's
Post design crossed with arm.ml's no-delay-slot call/cut_to ordering, at
whichever of the two widths the backend targets (riscv64.ml uses
Space.Standard64 like alpha.ml; riscv32.ml uses Space.Standard32 like
mips.ml - see riscv64.ml's/riscv32.ml's own header comments).

Register numbering follows the real RISC-V integer calling-convention
table (x0=zero, x1=ra, x2=sp, x3=gp, x4=tp, x5-x7=t0-t2, x8=s0/fp, x9=s1,
x10-x17=a0-a7, x18-x27=s2-s11, x28-x31=t3-t6), identical between RV64 and
RV32 - only the register *width* differs, not the numbering/ABI roles. x5/
t0 is reserved as this backend's own immediate-materialization scratch
register (not in vol_int/nvl_int), same role as mips.ml's $1/at, arm.ml's
r12/ip. x8/s0 is ALSO reserved out of nvl_int, proactively, even though
nothing in this session's hello-world milestone exercises it: this is the
same fix armcall.ml's r11/fp reservation made in the ARM session, for the
same reason (fork-tiger's gc.c, built with -fno-omit-frame-pointer, walks
s0 as a real frame-pointer chain across C--/C boundaries - letting the
register allocator reuse it would silently corrupt that chain the moment a
real program actually collects garbage). Applied here from the start
rather than rediscovered the way ARM's session found it, since the fix
costs nothing and the failure mode is identical.

Toolchain: RV64 only
---------------------
Ubuntu packages a real riscv64-linux-gnu gcc/binutils/glibc cross toolchain
(native 64-bit, no multilib trick needed - same situation as alpha's
gcc-alpha-linux-gnu), installed this session via `sudo apt install
gcc-riscv64-linux-gnu binutils-riscv64-linux-gnu libc6-dev-riscv64-cross`.
qemu-riscv64/qemu-riscv32 (user-mode emulation) were already present.

Ubuntu ships NO riscv32-linux-gnu package at all - confirmed via
`apt-cache search riscv`: only riscv64-linux-gnu-* packages exist. This
isn't a packaging oversight to work around - mainline Linux distributions
generally don't support a 32-bit RISC-V *userspace* (unlike ARM, where
32-bit has full distro support alongside 64-bit): there is no glibc built
for the ilp32 ABI in this toolchain's sysroot at all (confirmed directly:
`riscv64-linux-gnu-gcc -march=rv32imac -mabi=ilp32 -static t.c` fails with
"fatal error: gnu/stubs-ilp32.h: No such file or directory" - the ilp32
variant of libc headers simply isn't installed). So -riscv32 cannot be
verified the way every other backend in this fork is (a libc-linked binary
running end to end) - see "RV32 verification" below for what was done
instead.

New files
---------
Two near-identical directory trees, arch/riscv64/ and arch/riscv32/ (the
latter built by copying the former and mechanically narrowing every
wordsize-dependent literal - see "RV32 vs RV64: what actually differs"
below for the precise list). Both follow the exact same file breakdown as
arch/mips/, since mips.ml/mipscall.ml/mipscc.ml/mipsasm.ml/mipsbackend.ml
were the primary templates (crossed with arm.ml's no-delay-slot bits):
  - riscvNN.ml/.mli        - Target.t + Post postexpander (mips.ml's shape,
                              arm.ml's do_call/cut_to ordering)
  - riscvNNregs.ml/.mli    - Spaces (Space.Standard64 for riscv64,
                              Standard32 for riscv32), pc/cc locations,
                              rspace - split out to avoid a circular
                              dependency with RiscvNN, mirrors
                              mipsregs.ml/armregs.ml
  - riscvNNcc.ml           - T.cc_specs table: "C"/"C--"/"notail"/
                              "C-- thread" all dispatch to one calling
                              convention (a0-a7 args/return, s1/s2-s11
                              callee-saved, t1-t2/t3-t6 volatile - see the
                              header comment there for the full register
                              table and the s0/t0 reservation rationale)
  - riscvNNcall.ml/.mli    - Call.t builder, same C.incoming/C.outgoing
                              prolog/epilog/call_actuals/call_results
                              structure as mipscall.ml's `c`. sp_align=16
                              (the RISC-V psABI's stack-alignment
                              requirement, identical for ILP32 and LP64D)
  - riscvNNrec.mlb -> .ml/.mli
                            - camlburg instruction-selection grammar,
                              generated via `bin/ocamlburg
                              arch/riscvNN/riscvNNrec.mlb >
                              arch/riscvNN/riscvNNrec.ml` (not a dune rule,
                              same as every other *rec.ml in the tree).
                              Covers add/sub/and/mul, the ten eq/ne/lt/le/
                              gt/ge/ltu/leu/gtu/geu comparisons, base+
                              offset addressing (plus a bare-symbol operand
                              - a real RISC-V assembler pseudo memory
                              form), and plain direct/indirect calls/
                              branches/cuts. No or/xor/shift/div, no
                              floating point.
  - riscvNNasm.ml/.mli     - Asm.assembler: GNU-as-syntax ELF emitter, no
                              branch-delay-slot nop (unlike mipsasm.ml's),
                              closer to armasm.ml's/alphaasm.ml's shape.
                              Emits `.option norelax` at the top of every
                              procedure (see "Bugs found" below).
  - riscvNNbackend.ml      - the phase pipeline, copied from
                              mipsbackend.ml's/armbackend.ml's structure
                              (trim_unreachable_code -> Placevar.context
                              RiscvNN.placevars -> ... -> RiscvNN.X.cfg ->
                              ... -> Colorgraph.ralloc/Flowra.ralloc ->
                              layout -> Phases.rmvfp -> asm#cfg_instr ->
                              Phases.emit_data)
  - dune, Makefile         - new library cmm_arch_riscvNN, same shape as
                              arch/mips/'s own
  - demos/hello_riscv64.c-- (new) - same program as hello_alpha.c-- (its
                              closer template: also needs an explicit
                              `wordsize 64 pointersize 64` target pragma
                              and bits64 printf import, for the same
                              metrics-mismatch reason)
  - demos/hello_riscv32.c-- (new) - NOT the same program as hello.c--:
                              since there is no libc to link against (see
                              "Toolchain" above), this cannot import printf
                              at all. Instead it exercises a "C--"-
                              convention call between two procedures, an
                              if/else conditional branch, and integer
                              addition, and reports the result (333) as the
                              process exit code (masked to 8 bits: 77) -
                              see "RV32 verification" below.
  - demos/riscv32_start.s (new) - a hand-written freestanding ELF entry
                              point (no crt0, no libc) that calls main via
                              the plain RISC-V C ABI and exits via a raw
                              `ecall` syscall with main's own return value.
                              Needed only for -riscv32; RV64 uses the real
                              riscv64-linux-gnu-gcc-provided crt0/libc, no
                              hand-written stub required.

RV32 vs RV64: what actually differs
------------------------------------
Everything is identical except the numbers that are genuinely
wordsize-dependent (the whole rest of the design - register roles, calling
convention, addressing modes, mnemonics - is the same real RISC-V ISA at
two widths):
  - wordsize: 64 vs 32; Space.Standard64 vs Standard32 (riscvNNregs.ml)
  - register/memory cell width: Cell.of_size 64 vs 32
  - T.memory/the load-store suffix table: riscv64 has an extra "d" (ld/sd)
    entry RV32 doesn't (no 64-bit load/store instructions exist on RV32);
    correspondingly riscv64asm.ml's #value handles a 64-bit case (.dword)
    that riscv32asm.ml's does not
  - T.alignment/globals' default alignment: 8 vs 4
  - Reloc.width assert in riscvNNasm.ml's #addr: 64 vs 32 (a pointer-sized
    relocation, so it must track T.pointersize)
  - the 12-bit signed immediate range for addi/andi (imm12, -2048..2047) is
    UNCHANGED between the two - that field width is architecturally fixed
    regardless of xlen, not a wordsize-scaled quantity, so
    riscvNNrec.mlb's fits_imm12 is identical text in both files
  - sp_align (16) is also UNCHANGED - the RISC-V psABI mandates 16-byte
    stack alignment for both ILP32 and LP64D

Bugs found and fixed while bringing this up
---------------------------------------------
- riscv64rec.mlb's fits_imm12 helper, written as the obvious
  `n >= -2048L && n <= 2047L` (n : int64, from Bits.S.to_int64), failed to
  typecheck once compiled as part of the whole riscvNNrec.mlb %head block
  in this project's build: "This expression has type int64 but an
  expression was expected of type int", pointing at the bare `n` on the
  left of `>=`. A standalone repro of the same two lines in a bare `ocaml`
  toplevel typechecks fine, and grepping the whole tree found no `-open`
  flag or Nopoly-style shadow of `(>=)`/`(<=)` that would explain a
  monomorphic-int bias - the exact mechanism was not root-caused further
  (this didn't block anything: no existing backend's .mlb head compares
  int64 values with the polymorphic operators, so there was no established
  precedent to compare against). Fixed by using `Int64.compare n (-2048L)
  >= 0 && Int64.compare n 2047L <= 0` instead, which sidesteps the
  polymorphic operators entirely and compiles cleanly.
- riscv64-linux-gnu-as's default assumes the C (compressed) extension is
  live (RV64GC), meaning the assembler/linker are entitled to relax
  ordinary instructions into 2-byte compressed forms or otherwise adjust
  encodings at link time. This backend's own hand-computed ra_offset=4
  (riscvNN.ml's Post.do_call, matching jal/jalr's hardware-guaranteed
  rd:=pc+4) assumes every jal/jalr it emits is exactly 4 bytes and nothing
  shifts around it afterward. Fixed proactively (not from an observed
  failure - hello.c-- is too small a program to have exposed a real
  divergence) by emitting `.option norelax` at the top of every procedure
  in riscvNNasm.ml's #cfg_instr, pinning the assembler to fixed-width,
  non-relaxed encodings - the same class of proactive fix as this fork's
  now-familiar #section ALLOC-flag fix for pcmap/pcmap_data.

RV64 verification
------------------
  ./bin/qc -riscv64 -globals -o hello_riscv64 demos/hello_riscv64.c--
  qemu-riscv64 ./hello_riscv64
    -> prints "hello, world!", exits 0

Checked in all three invocation styles this fork's convention expects: the
3-step form (qc -stop .s, then riscv64-linux-gnu-as, then
riscv64-linux-gnu-gcc -static), the one-shot `-ld "riscv64-linux-gnu-gcc
-static"` form, and the plain default (QC_AS/QC_LD unset, relying on
default_riscv64_cc) via `demos/Makefile`'s own riscv64/run-riscv64 targets.
All three produce a binary that runs correctly under qemu-riscv64.

RV32 verification
------------------
Since there is no libc for this width (see "Toolchain" above),
demos/hello_riscv32.c-- cannot be linked the way every other backend's
demo is. Verification is freestanding instead: qc compiles the .c-- source
down to a plain .o (no crt0 involved), which is linked directly against a
hand-written _start (demos/riscv32_start.s, see "New files" above) using
riscv64-linux-gnu-as/-ld invoked as bare cross tools (not through the gcc
driver, so no libc/sysroot is ever consulted):

  qc -riscv32 -globals -stop .o -o hello_riscv32.o demos/hello_riscv32.c--
  riscv64-linux-gnu-as -march=rv32imac -mabi=ilp32 \
    demos/riscv32_start.s -o riscv32_start.o
  riscv64-linux-gnu-ld -m elf32lriscv -static -e _start \
    -o hello_riscv32 riscv32_start.o hello_riscv32.o
  qemu-riscv32 ./hello_riscv32; echo $?
    -> exits 77 (222+111, masked to 8 bits - see hello_riscv32.c--'s own
       comment for the exact computation)

This exercises the same core machinery hello_riscv64.c-- does (procedure
calls via the "C--"/"foreign C" conventions, the full prolog/epilog stack
frame, register save/restore) plus one thing hello_riscv64.c-- does NOT
exercise: an if/else conditional branch (bc_guard/bc_of_guard/negate),
since hello.c---style programs have no control flow of their own. This is
believed to be at least as strong a smoke test as any other backend's
hello-world milestone, just measured by exit code instead of stdout.

A single `qc -riscv32 ... riscv32_start.s hello_riscv32.c--` one-shot
invocation (passing both source files together, the way `qc -globals -o
hello runtime.o stdlib.a hello.c--` mixes prebuilt objects with one source
file elsewhere in this project) does NOT work: main_action names each
compiled input's intermediate .o after the single shared `-o` name rather
than each input's own basename, so two *sources* needing compilation in
the same invocation collide and overwrite each other's object file. This
is pre-existing driver behavior, not something introduced or fixed in this
session - worth knowing about if anyone else tries to feed qc multiple
uncompiled inputs at once, but out of scope to fix here (demos/Makefile's
riscv32 target works around it with three separate rules instead of one).

RV32 tiger-suite bring-up: 15/15
-----------------------------------
Following up the hello-world pass above, tests/run-tiger-riscv32.sh now
passes all 15 tests (arrays, colmajor, exceptions, forloop, funcall, hello,
merge, qsort, queens, rc4, rb, rbshort, sieve, wf, wff) - see
expected/tiger-riscv32.txt. This beats every other non-x86/ppc backend's
own baseline (arm 6/15, mips/sparc 1/15 each) and matches ppc's 15/15.
RV64 tiger tests were deliberately NOT attempted, on the same structural
grounds as alpha's own tiger blocker (see alpha-backend-status in memory,
or the git history around alpha's bring-up): fork-tiger's runtime hardcodes
bits32 pointers throughout, so a 64-bit target hits the identical
32-vs-64-bit mismatch alpha did - not investigated here since the user
confirmed this scope decision ("probably will work just for riscv32
because tiger does not have a 64 backend yet").

RV32's tiger runtime is picolibc-based, same as its hello-world milestone
(no glibc for this width - see "Toolchain" above), needing the same
gcc-riscv64-unknown-elf + picolibc-riscv64-unknown-elf toolchain and the
same -nostartfiles/custom-_start discipline, but scaled up: tiger's runtime
(fork-tiger's runtime.c--/alloc.c--/stdlib.c/gc.c, plus this fork's own
runtime.c/pcmap.c/gcc-linux.c) needs a real printf/malloc/exit surface, not
just the trivial one hello_riscv32.c-- exercised. Bugs found bringing this
up, roughly in the order hit:

1. NUM_REGS/FP_REG overflow (runtime/qc--runtime.h, runtime/gcc-linux.c).
   Cmm_Activation's `regs[NUM_REGS]` array is indexed by target.ml's own
   flat register numbering (mk_reg_ix_map: every Reg/Fixed-classified
   space, SORTED BY SPACE CHARACTER - 'c' < 'f' < 'r' - not by the order
   a backend's own `spaces` list happens to list them in), and
   update_saved_regs writes into it with NO bounds check. The x86-sized
   default (NUM_REGS=12) silently overflows for RISC-V's own space sizes
   (c=6, f=32, r=32 -> 70 flat indices needed) - the exact same overflow
   bug already fixed for ppc/sparc, just never yet hit for RISC-V. Fixed
   by adding a `#elif defined(__riscv)` branch (NUM_REGS=96, matching
   ppc's own headroom margin) covering both RV32 and RV64 (same register
   topology, only value width differs). gcc-linux.c's FP_REG (the flat
   index gcc's own -fno-omit-frame-pointer C code uses as a walkable
   frame-pointer chain across C--/C boundaries) similarly needed its own
   RISC-V entry: s0/x8 (the register riscv32cc.ml/riscv64cc.ml already
   reserve out of nvl_int for exactly this reason - see the "What this is"
   section above) sits at flat index c(6)+f(32)+8 = 46, not the x86-
   shaped default's 9. Both numbers were derived by formula (not
   empirically probed via gdb the way ppc's own 72 was pinned down
   originally) but cross-checked against ppc's own confirmed 96/72 pair -
   applying the identical sort-by-space-character derivation to ppc's
   space sizes reproduces its documented 72 exactly, which is why this
   was trusted enough to apply proactively. Confirmed indirectly by the
   full suite passing (a wrong FP_REG would show up immediately in any
   GC-crossing test, and 11 of the 15 tests here do cross that boundary).

2. gp (the global pointer) needs real initialization in the freestanding
   crt0, or every gcc-compiled C object here (picolibc itself, and fork-
   tiger's own stdlib.c/gc.c once regenerate-riscv32.sh compiles them)
   segfaults immediately. GCC's default RV32 codegen uses gp-relative
   loads/stores ("lw rd, offset(gp)") for small global/static data - a
   compile-time codegen choice independent of the assembler's own
   link-time relaxation, so `.option norelax` (already used elsewhere in
   this backend) does nothing to prevent it. With gp left at whatever the
   kernel handed the process at entry (effectively 0), any such access
   reads/writes near address 0 - confirmed empirically: SIGSEGV at
   si_addr=0xfffff820, i.e. gp=0 plus a small negative 12-bit offset,
   wrapping to just under 4GB. Fixed in runtime/riscv32_crt0.s with the
   standard idiom (also what picolibc's own crt0.o does, confirmed by
   disassembling it): `.option push / .option norelax / la gp,
   __global_pointer$ / .option pop` before anything else runs - the local
   norelax scope is required around exactly this instruction, since
   without it the assembler could "relax" this very load into a
   gp-relative reference to itself. Notably, qc's OWN generated code never
   needed this (it doesn't do small-data/gp-relative optimization at all),
   so demos/riscv32_start.s never needed the fix - this only bites once
   real gcc-compiled C objects enter the link, which tiger's runtime is
   the first thing in this session to actually require.

3. picolibc's libc.a does not itself define stdout/stdin/stderr in this
   packaging (confirmed via `readelf -s` on every candidate .o - e.g.
   libc_tinystdio_bufio.c.o only WEAKLY REFERENCES them, `UND` in every
   object in the archive, never a real definition) - printf.o's own
   reference to `stdout` is `U stdout` and just stays unresolved. This is
   picolibc's normal "hosted" integration point: the platform integrator
   is expected to supply the three streams via the documented
   FDEV_SETUP_STREAM macro (a FILE struct built from put/get byte
   callbacks - unbuffered by construction, one call per character, no
   separate buffering layer to worry about flushing). Added to
   runtime/riscv32_syscalls.c: con_put/con_get/err_put wrapping the raw
   _write/_read syscalls, and `FILE *const stdout = &con_out;` etc.
   (confirmed unbuffered behavior directly: a printf immediately followed
   by abort() still shows the printf's output).

4. picolibc's malloc doesn't call the newlib-style `_sbrk` this backend
   already provided - it calls the POSIX-named `sbrk()` directly
   (libc_picolib_picosbrk.c.o), which in ITS default form wants linker-
   provided `__heap_start`/`__heap_end` symbols that only exist under
   picolibc.ld's own memory-map layout (see bug 5 below for why that
   layout is unusable here at all). Fixed by renaming the existing
   static-array bump allocator to `sbrk` (POSIX name) with `_sbrk` now
   just forwarding to it - a strong definition of `sbrk` means the linker
   never needs to pull picolib_picosbrk.c.o from the archive at all,
   sidestepping the __heap_start/__heap_end requirement entirely rather
   than trying to satisfy it.

5. Two DISTINCT problems, both caused by linking through
   `riscv64-unknown-elf-gcc --specs=picolibc.specs` instead of plain `ld`
   directly, both found empirically (not anticipated):
     a. picolibc.specs' `*link` spec injects `-Tpicolibc.ld` unless -T is
        given explicitly. picolibc.ld lays out a bare-metal-style
        flash+RAM memory map (with ROM-to-RAM .data copy semantics that
        only picolibc's own crt0 - which this backend deliberately
        doesn't use - performs) at a load address (0x80000000) that plain
        qemu-riscv32 user-mode emulation cannot run: confirmed via
        `readelf -l` (two PT_LOAD segments with differing VirtAddr/
        PhysAddr, i.e. genuine flash-vs-RAM addresses, meaningless outside
        a real memory-mapped microcontroller) and empirically (SIGSEGV
        before even reaching main).
     b. Passing an explicit `-T` to work around (a) does NOT disable the
        SAME spec's unconditional `--gc-sections`, which silently
        discards INDIVIDUAL .pcmap/.pcmap_data entries (not the whole
        section - confirmed via readelf: the entry for fork-tiger's own
        runtime/alloc.c--'s `tig_call_gc`'s "cuts to k" continuation was
        missing from the FINAL LINKED BINARY even though it was
        confirmed present, via `objdump -dr`, in alloc.o's own .pcmap
        section before linking). pcmap.ld's Cmm_pc_map/Cmm_pc_map_limit
        symbols still bound a correctly-SIZED region either way -
        --gc-sections's liveness analysis simply doesn't understand that
        a linker-script address-range reference (not an ordinary symbol
        reference) is what keeps an individual .pcmap entry meaningful,
        so entries with no other referrer get treated as dead code and
        dropped. This manifested as `assert(entry)` failing in runtime.c's
        Cmm_YoungestActivation (SIGABRT, "assertion \"entry\" failed") -
        confirmed by temporarily logging the failing pc: it was exactly
        alloc.c--'s own `_Lcut_entry_l8` label, the "continuation k():"
        target `tig_call_gc` cuts to once GC finishes - i.e. every single
        test that allocates enough to trigger a real collection hit this
        (11 of 15 tests failed with the identical symptom before this
        fix, 0 after).
     Fixed by abandoning `riscv64-unknown-elf-gcc --specs=picolibc.specs`
     for the FINAL LINK step entirely (kept only for compiling, where its
     include-path setup is still wanted) - tests/run-tiger-riscv32.sh now
     links with plain `riscv64-unknown-elf-ld` directly (no picolibc.ld
     injection since nothing asks for it, no --gc-sections), adding
     -L/--start-group -lc -lgcc --end-group explicitly, with the library
     directories derived from the installed toolchain (`gcc
     -print-libgcc-file-name`, `gcc -print-multi-directory` composed with
     picolibc's known install layout) rather than hardcoded, so this
     survives a toolchain version bump. Note: `ld` still prints a
     "contains output sections; did you forget -T?" warning about
     pcmap.ld even in this fixed form - confirmed harmless (the actual
     runtime behavior is correct with or without an explicit -T once
     --gc-sections is out of the picture; the warning was a red herring
     during this investigation, not the real bug).

6. riscv32rec.mlb was missing `%quot` (integer division) entirely -
   sieve.c--/colmajor.c--/merge.c-- all genuinely divide, unlike either
   hello demo. Added RV32M's native `div` instruction (truncating,
   round-toward-zero - the same semantics %quot already assumes, so no
   sign-fixup needed) plus the same [1]-cost li-then-op immediate
   fallback add/sub/and/mul already have, in both riscv32.ml's
   T.capabilities and riscv32rec.mlb - not extended to riscv64 in this
   pass (out of scope: RV64 tiger tests weren't attempted, see above), so
   riscv64's own capabilities list is now narrower than riscv32's until
   something actually needs div there too.

Known remaining gaps
---------------------
- -O3 compiles cleanly for both widths (`qc -riscv64/-riscv32 -O3 ...`
  exits 0 and produces assembly) but the resulting RV64 binary HANGS at
  runtime under qemu-riscv64 (verified: a 10-second `timeout qemu-riscv64
  ./hello_riscv64_O3` times out, exit 124). Not investigated - same
  situation notes_arm.txt documents for ARM's own -O3 hang (-O0, the
  default, is what's verified everywhere else in this fork too). RV32
  -O3 was not run under qemu at all this session (only confirmed the
  compile step succeeds).
- RV64 tiger tests not attempted at all (see "RV32 tiger-suite bring-up"
  above) - blocked on the same bits32-pointers-in-a-64-bit-runtime
  mismatch as alpha, not investigated further per explicit scope
  agreement with the user.
- riscv64rec.mlb's operator coverage (add/sub/and/mul, no quot/or/xor/
  shift, no floating point) is now narrower than riscv32rec.mlb's (which
  also has quot) purely because RV64 tiger tests were never attempted to
  drive out what else it would need - see item 6 above.
- The fits_imm12/imm[1]-cost fallback pattern (materializing an
  out-of-range addi/andi immediate via `li t0, ...` then a register-
  register instruction) and the analogous Cmp(op,x:reg,y:const) branch-
  against-constant fallback, in both riscvNNrec.mlb files, are modeled on
  alpharec.mlb's/armrec.mlb's precedent but STILL not known to be
  exercised by anything run so far (all 15 tiger programs' immediates/
  frame sizes stayed small) - unverified beyond compiling without error.
  If a future program's stack frame or constant exceeds the 12-bit
  window, this is the first place to check.
- The NUM_REGS=96/FP_REG=46 fix (see item 1 above) was derived by formula
  and cross-checked against ppc's own numbers, not independently
  confirmed via a from-scratch gdb probe the way ppc's original 72 was.
  The RV32 tiger suite passing end to end (11 of 15 tests genuinely cross
  the C boundary during a real GC) is strong indirect evidence it's
  right, but if something GC-related ever misbehaves on either RISC-V
  width, this is worth re-deriving from first principles rather than
  assumed correct forever.
- This session's NUM_REGS/FP_REG investigation strongly suggests mips.ml
  and arm.ml have the SAME latent bug (both default to the unmodified
  x86-sized NUM_REGS=12/FP_REG=9, and both have register-space layouts
  at least as large as RISC-V's - mips: r=32/f=32/c=6, same 70-index
  need; arm: r=16/c=3, still exceeds 12) - not fixed here (out of scope:
  those backends were not touched this session, and fixing them needs
  its own verification pass against their own tiger baselines), but
  worth flagging: this may be a real, currently-unexplained contributor
  to notes_arm.txt's own "6/15, root cause is a shared liveness bug"
  finding, not necessarily a fully separate issue from what's described
  there.
