notes_arm.txt
==============

Written: 2026-08-17, against commit 9b7e407 (parent of the commit that adds
this file and the ARM backend itself). All claims below are VERIFIED: read in
the code, or observed by actually running `qc -arm ...` under qemu-arm, not
inferred from upstream Lua.

What this is
------------
ARM is the fifth non-x86 backend plugged into this fork, after ppc, sparc,
alpha, and mips. Unlike those four, upstream qc-- never finished ARM: its
src/ only ever had arm.nw (the Target.t description, ~466 lines). There is
no armregs.nw, armcall.nw, armasm.nw, or armrec.nw anywhere upstream. So this
was new development modeled on the sibling backends' *current* (post-fork)
shape, not a port of existing .nw content - that's why every new file below
is plain source with no syncweb (*s:*)/(*x:*)/(*e:*) markers, and why
arch/arm/Makefile's SRCNW still lists only "arm".

Target shape (verified in arch/arm/arm.ml)
-------------------------------------------
- 32-bit little-endian, 16 general registers r0-r15 (r13=sp, r14=lr/ra,
  r15=pc). No FPU: T.float = Float.none, and Post.unrm/binrm/fcontext/
  rcontext are all Impossible.unimp "no floating point on ARM".
- Condition-code model, architecturally like SPARC and unlike MIPS: a single
  `cc` pseudo-location set by arm_subcc, consumed by named condition
  operators (arm_eq/arm_ne/arm_lt/arm_le/arm_gt/arm_ge/arm_ls/arm_hi).
  sparcrec.mlb was the closer template than mipsrec.mlb for this reason,
  even though mips*.ml files (which are complete and current) were the main
  template for everything else.
- arm.ml pre-existed this work but targeted a stale pre-fork interface (old
  PX.Nop/PX.Rtl instead of Dag, a single bc instead of bc_guard/bc_of_guard,
  call/callr that never stored ra, effect-list cut_to, a target record shaped
  for the pre-Preast2ir.T Target.t). Fixed to match what mips/sparc/alpha
  already migrated to. Every (*s:*)/(*x:*)/(*e:*) marker in the file was left
  untouched - only chunk *contents* changed, never chunk boundaries.

New files (arch/arm/), no upstream .nw counterpart
----------------------------------------------------
- armregs.ml/.mli    - Spaces (SS.c 3 id [32], "pc, _, cc" - no npc/delay
                        slot unlike mips, no f/u FP spaces), pc/cc locations,
                        rspace. Split out of arm.ml (mirrors mipsregs.ml)
                        specifically to avoid a circular dependency with Arm.
- armcc.ml           - T.cc_specs table: "C"/"C--"/"notail"/"C-- thread" all
                        dispatch to one calling convention (modeled directly
                        on mipscc.ml's shape).
- armcall.ml/.mli    - Call.t builder. r0-r3 = args/volatile, r4-r11 =
                        callee-saved, r12/ip = scratch, r13/r14 = sp/lr.
                        sp_align = 8 (AAPCS). Same C.incoming/C.outgoing
                        prolog/epilog/call_actuals/call_results structure as
                        mipscall.ml's `c`.
- armrec.mlb -> armrec.ml/.mli
                     - camlburg instruction-selection grammar, generated via
                       `bin/ocamlburg arch/arm/armrec.mlb > arch/arm/armrec.ml`
                       (that generation command is not a dune rule - same as
                       every other *rec.ml in the tree, regenerate by hand).
                       Only a minimal operator set is covered: add/sub/and +
                       comparisons, base+offset addressing. ldrsb/ldrb-style
                       sign/zero-extending sub-word load rules exist in the
                       grammar but are unreachable from any Expander call
                       site actually exercised by hello_arm.c-- - the same
                       latent gap mips's own Sx/Zx rules have.
- armasm.ml/.mli     - Asm.assembler: GNU-as-syntax ELF emitter. No branch-
                        delay slot (unlike mips/sparc), so #call has no
                        trailing nop, closer to alphaasm.ml/ppcelfasm.ml's
                        shape than mipsasm.ml's.
- armbackend.ml      - the phase pipeline (trim_unreachable_code ->
                        Placevar.context Arm.placevars -> ... -> Arm.X.cfg ->
                        ... -> Colorgraph.ralloc/Flowra.ralloc -> layout ->
                        Phases.rmvfp -> asm#cfg_instr -> Phases.emit_data),
                        copied from mipsbackend.ml's structure.
- dune               - new library cmm_arch_arm, same libraries list shape as
                        arch/mips/dune.

Toolchain
---------
Unlike sparc/mips (clang cross-assembles but there's no local sysroot for
real static linking) and alpha (no default cc at all, must pass -as/-ld by
hand), Ubuntu ships a real arm-linux-gnueabihf gcc cross toolchain on this
machine, so default_arm_cc is just "arm-linux-gnueabihf-gcc" - both
assembler and linker, no clang workaround needed. qemu-arm (user-mode
emulation) runs the resulting static binary directly.

Bugs found and fixed while bringing this up
---------------------------------------------
- arm-linux-gnueabihf-as's comment character is "@", so
  `.section "x","a",@progbits` (the form mips/ppc/sparc/alpha all use) had
  its @progbits silently swallowed as a comment. GNU as on ARM wants
  %progbits instead. Without the ALLOC flag actually landing, pcmap/
  pcmap_data data fell outside every PT_LOAD segment (same failure mode
  documented for the other backends' #section fix).
- ARM's data-processing instructions can only encode an 8-bit value rotated
  by an even number of bits as an immediate operand - arbitrary 32-bit
  constants (e.g. a large stack-frame size in `add sp, sp, #N`) don't fit
  that encoding and the assembler rejected them. Fixed by materializing such
  immediates through `ldr ip, =value` (an assembler pseudo-op that picks
  mov/mvn/a PC-relative literal-pool load as appropriate) instead of trying
  to emit them as literal #N operands. Same fix incidentally required
  switching const32's printer to signed decimal, which also fixed negative
  [reg, #imm] load/store offsets.

Verification performed
-----------------------
  ./bin/qc -globals -arm -o hello_arm demos/hello_arm.c--
  qemu-arm ./hello_arm
    -> prints "hello, world!", exits 0

Checked in three invocation styles: the plain default (no -as/-ld), and the
one-shot `-ld "arm-linux-gnueabihf-gcc -static"` form. All three produce a
binary that runs correctly under qemu-arm.

Modified files
--------------
- arch/arm/armrec.mlb / arm.ml - added %mul and %quot (sdiv) support: new
  conMul/conQuot exp cases, register-register and register-immediate inst
  rules (the immediate forms go through the same "ldr ip, =y" trick add/sub/
  and's immediate rules already use, since ARM's mul/sdiv only take register
  operands), "mul"/"quot" added to T.capabilities.operators. Also added "le"
  (was missing - lt/gt/ge were declared but plain signed le wasn't, an
  oversight in the original hello.c---only capabilities list) and "sx"/"zx"
  from width 1 + "bit" (empty-width markers, matching sparc.ml's/x86.ml's own
  declarations) - these last three are cosmetic (codegen/expander.ml's
  Sx/Zx(Bit(e)) boolean-materialization case is a structural RTL-shape match
  that fires unconditionally, not gated by T.capabilities at all - confirmed
  by testing) but silence spurious "No acceptable widths for %sx" mvalidate
  warnings that were otherwise cluttering every compile.
- arch/arm/armasm.ml - literal-pool management. Two related bugs, both real:
  (1) `ldr rX, =imm` (used for essentially every non-trivial immediate) is a
  PC-relative load from a GNU-as-managed literal pool, which as defaults to
  placing at the very end of .text - too far (>4KB, "invalid literal
  constant: pool needs to be closer") from an early reference in a function
  as large as tests/tiger/colmajor.c--'s. Fixed with a ".ltorg" after every
  function body (#cfg_instr). (2) That alone wasn't enough for tests/tiger/
  rb.c--'s larger functions - added a periodic in-function pool too: an
  instruction-line counter (approximating 4 bytes/line, with multi-line
  "ldr ip,=y\n\top ..." rules counted as 2+) that drops a "b .LpoolN /
  .ltorg / .LpoolN:" (branch-guarded, so control never falls into the pool
  data) once accumulated bytes exceed a conservative 3000-byte budget. Fixed
  all 15 tests/tiger/ programs' compile+link step (0 compile/link failures
  remain, was previously 2-11 depending on which other fixes were applied
  first).
- arch/arm/armcall.ml - two allocatable-register-set fixes, both real ABI-
  correctness issues, found by inspection while investigating the runtime
  failures below (NOT the root cause of what's still failing - see "Root
  cause CONFIRMED" further down, a shared cross-backend bug unrelated to
  either of these - but both are genuine bugs worth having fixed regardless,
  and a before/after test run confirmed neither one, by itself, changed the
  pass count):
    (1) r12/ip was in vol_int (allocatable) despite armrec.mlb's every
        immediate-materialization rule using it as unconditional scratch -
        the same class of bug mips.ml's $at (r1) reservation already avoids
        (see mipscall.ml's own vol_int, which starts at 2 not 0). Removed.
    (2) r11/fp was in nvl_int (allocatable) despite fork-tiger's gc.c being
        compiled with -fno-omit-frame-pointer specifically so its collector
        can cross C--/C frame boundaries by walking r11 as a real AAPCS
        frame-pointer chain (see fork-tiger/pad.txt, this project's own
        CLAUDE.md). Removed (nvl_int now stops at r10).
  Toolchain: default_arm_cc/CCARM bumped to "-march=armv7ve+fp" everywhere
  (driver/main.ml, demos/Makefile, runtime/Makefile's arm branch, tests/
  tiger/regenerate-arm.sh) - plain armv7-a (this toolchain's own default)
  has no integer divide instruction at all ("sdiv"/"udiv" fail to assemble,
  needed once %quot started emitting them); "+fp" is not optional on top of
  that - "-march=armv7ve" alone drops the "+fp" the plain default carries,
  and -mfloat-abi=hard (this toolchain's own default ABI) then refuses to
  compile any real C source at all ("selected architecture lacks an FPU") -
  only bites once real C gets compiled (runtime.c/gc.c/stdlib.c), which
  demos/hello_arm.c--'s pure assemble+link path never did, hence why this
  wasn't caught during the first pass. Confirmed a strict superset - re-ran
  demos/hello_arm.c-- and `make -C demos run` (all 6 arches) after the bump,
  no regression.
- runtime/Makefile - new arm branch (CC32, CONTOBJ=armcont.o, QCFLAG=-arm),
  float "none" splice in the $(B)/%.c-- rule (same sed trick as above,
  generalized to handle stdlibcmm.c--'s extra "memsize/wordsize/pointersize"
  clauses on the target line too, not just the plain form runtime's own

Stack-protector false positive
-------------------------------
gcc's default stack-protector on the C side (runtime.c/pcmap.c/gcc-linux.c
via runtime/Makefile, gc.c/stdlib.c via regenerate-arm.sh) was spuriously
firing ("*** stack smashing detected ***: terminated") against every
tests/tiger/ program past the 4 simplest ones, aborting before any output.
Confirmed by hand (colmajor/sieve were the test cases) that this is the
canary check itself false-tripping: SP stays a multiple of 8 everywhere
checked (ruling out the usual AAPCS-alignment cause), and disabling the
check entirely (which is what -fno-stack-protector, now applied, does) was
the thing that got sieve/arrays/exceptions/forloop/funcall/hello passing
with genuinely correct, byte-for-byte-matching output - not just "no longer
crashing". Root cause of the false trip itself not pinned down further
(most likely something about this backend's calling-convention codegen that
gcc's canary placement doesn't expect) - a real gap, but disabling the check
on this backend's own C-side test/demo runtime specifically (not a global
change, not shipped code) was judged the pragmatic fix for a stretch-goal
pass rather than chasing gcc-generated ARM canary codegen line by line.

Root cause CONFIRMED: a shared, pre-existing GC/register-allocator bug,
not ARM-specific
--------------------------------------------------------------------------
(Written after a follow-up session, same day, still commit-adjacent to the
6/15 pass above.) The remaining 9/15 failures - both the "array index N for
array of size 0" cluster (colmajor/qsort/queens/rc4) and the "tig_compare_str:
t is null" cluster (rb/rbshort/wf/wff/merge) - trace to a single root cause,
and it is NOT specific to this ARM backend.

Diagnosis: temporarily patched a scratch copy of fork-tiger's gc.c (restored
immediately after each patch, diff-verified clean both times - never left
modified) to log every time the collector's tig_gc() actually fires, and
what Cmm_ChangeActivation's stack-walk finds. For colmajor specifically:
  - tig_gc DOES fire (the heap is only 8192 bytes per semispace by default,
    and colmajor's `lines := stringlist[1024] of ""` alone - the array that
    later comes back "size 0" - eats over half of that on its own, so it
    doesn't take much more allocation, e.g. from string-building while
    reading stdin, to exhaust it).
  - tig_gc's `bzero(from_space, heap_size)` (runtime/gc.c - this is a
    COPYING/semi-space collector: live data gets relocated to to_space, then
    the whole old from_space is zeroed unconditionally) runs against
    from_space=0x72dc8 - exactly the array's own address region.
  - But Cmm_ChangeActivation's stack-walk (runtime/runtime.c's
    normal_change) finds only ONE activation (tig_call_gc's own trivial
    frame, var_count=0, no gc_data - which is expected, alloc.c--'s
    tig_call_gc declares no Tiger-visible locals of its own) and then STOPS -
    it never walks further up to tig_alloc's actual Tiger-level caller,
    which is where the live `lines` root would have been found and
    relocated. So nothing gets copied, and the still-live array gets wiped
    by the unconditional bzero right along with the genuinely-dead old
    generation - a real, observable memory-safety bug, not corruption from
    a compiler-arithmetic mistake (my earlier working note in this file,
    since corrected, had misread this as an off-by-one in colmajor's
    cmfirst_49/cmnext_50 iterator - it isn't; the array's own header/data
    genuinely change value in place between GC-adjacent calls).

The walk in normal_change reads the return address from a stack location
described by pcmap's `return_addressp` field for the current procedure - a
location computed from the SAME architecture-independent path on every
backend (codegen/ast2ir.ml's `saved_ra`, via `C.where_to_save_ra`, which
arm.ml/mips.ml/ppc.ml/sparc.ml all implement identically:
`Talloc.Multiple.loc t 't' width`, an ordinary temp-allocator request with
no "must stay live across every call in this procedure, for GC safety" flag
attached). That temp's FINAL location is decided later by each backend's own
register allocator based on ordinary liveness - and an ordinary allocator is
entitled to reuse that register/slot for something else the moment its
normal liveness analysis considers the return-address value dead, which can
easily be well before every OTHER call site in the same procedure (GC can
happen at ANY call, not just the ones "close enough" to entry/exit that
liveness naturally keeps it around for). Under high register pressure this
reuse actually happens, corrupting what the pcmap descriptor still claims is
the return-address slot.

This reframes the whole investigation: it's not a bug in armrec.mlb, arm.ml,
armcall.ml, or armasm.ml - none of the fixes made in the first two passes
(operator coverage, literal pools, r11/r12 reservations, toolchain march) are
wrong to have made, but none of them touch the actual defect, which lives in
shared codegen/register-allocation machinery that has nothing backend-
specific about its INTENT (only its manifestation is register-pressure-
dependent, hence backend-dependent in practice).

Confirming cross-backend evidence: this project's own already-recorded
baselines (tests/expected/tiger-{mips,sparc}.txt, both checked in well before
this session) show mips at 1/15 (only hello) and sparc at 1/15 (only sieve) -
the exact same failure shape, on backends that predate this session entirely
and were never touched here. ppc alone reaches 15/15 - not because ppc's
C.where_to_save_ra does anything different (arch/ppc/ppc.ml's is textually
the same `Talloc.Multiple.loc t 't' ws` pattern) but almost certainly because
ppc has roughly twice the general-purpose registers (32 GPRs vs. 16 on
ARM/MIPS/SPARC, several of which are further reserved for sp/lr/pc/a
backend's own scratch use), giving its register allocator enough headroom to
essentially never need to reuse the return-address temp's register within
these particular small test programs - sidestepping the bug by luck of
register count, not fixing it.

Ruled out along the way (in case revisited): NOT the %mul/%quot grammar
additions (a targeted register+immediate smoke test of both passed
correctly, including the exact truncating-division semantics needed); NOT SP
alignment (checked directly in generated .s, always a multiple of 8); NOT
the literal-pool/.ltorg mechanism (checked its insertion points land between
complete call+successor-label pairs, never splitting one); NOT the r12/r11
allocatable-register fixes from the first tiger-suite pass (both correct
ABI-compliance fixes, confirmably zero effect on the pass count by
themselves). GDB-under-qemu's-gdbstub proved unreliable for this
investigation (breakpoints either failed to fire or changed program behavior
vs. an unmodified run - some kind of stub/timing interaction, not chased
further); source-level (gc.c) print instrumentation, restored immediately
after each use, was what actually produced trustworthy data.

Scope decision: presented this finding to the user (it is a deep,
cross-backend liveness/register-allocation correctness gap - fixing it
properly means teaching the compiler that a GC-relevant temp like saved_ra
must be treated as live across every call in its procedure regardless of
ordinary dataflow liveness, touching codegen/ast2ir.ml and/or regalloc/ code
shared by every backend, with real regression risk to ppc/x86/sparc/mips/
alpha, which currently all build on the same machinery) - decision was to
stop at 6/15 for now rather than pursue the deep fix in this session. ARM
already exceeds mips's and sparc's own tiger-suite baselines (1/15 each)
despite being the newest backend, so 6/15 is not a backend-specific
shortfall to feel behind about.

Not attempted
-------------
- The actual fix: making the return-address-holding temp (and in principle
  any other GC-required-to-be-findable location) genuinely live across every
  call site in its procedure, not just where ordinary liveness happens to
  keep it. Natural places to start: codegen/ast2ir.ml's `saved_ra`/`spans`
  construction (~line 200-215, ~395-400), and whatever regalloc/ liveness
  pass currently computes interference without knowing about this
  requirement - Colorgraph.ralloc/Flowra.ralloc's inputs (a Dataflow.t or
  similar liveness result computed upstream of both) are the likely places
  to look next.
- Whether fixing this would actually bring arm to something close to ppc's
  15/15 (plausible, since ppc's own success looks incidental to register
  count rather than a genuine different mechanism, but not verified) or
  whether other, still-undiscovered bugs remain underneath.
- -O3 (already a known gap from the first pass, unaffected by this one).
