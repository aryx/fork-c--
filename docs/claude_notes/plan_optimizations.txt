plan_optimizations.txt — what optimizations would improve generated-code
performance, given opti/ is thin today
Written 2026-08-17, against commit ec9f990.

Prompted by: "then what optimizations we could to improve performance of the
generated code? the optimizer/ directory does not contain much code yet"
(the actual directory is `opti/`, not `optimizer/`).

Verified: what opti/ (and its dataflow dependencies) already does
--------------------------------------------------------------------
From `opti/optimize.ml`, `opti/peephole.ml`, `cfg/dataflow/*`:

- `simplify_exps` — local constant folding, one RTL at a time (`Simplify.rtl`).
- `trim_unreachable_code` — postorder-DFS reachability, deletes unreached
  blocks. Cleanup, not perf-critical.
- `collapse_branch_chains` — jump-to-jump threading (chase a chain of
  empty branch-only blocks to the final real target).
- `remove_nops` — deletes `Kill`s and redundant self-stores.
- `validate` — checks every RTL is a legal target instruction; not an
  optimization, a well-formedness pass.
- `elim_dead_assignments` — real backward dead-store elimination:
  `Dataflow.B.a_t Live.live_in Dead.elim_assignments`, run to a fixpoint via
  the generic `Dataflow.B.rewrite` (backward analysis, no entry_fact).
- `Peephole.subst_forward` (opti/peephole.ml) — forward copy/constant
  propagation: uses `Availpass` (a real available-expressions dataflow
  analysis, `Dataflow.F`) to find a location's known value and substitutes
  it into later RTLs, then re-simplifies with `Simplify.rtl`.
- Register allocation: Chaitin/Briggs-style graph coloring
  (`regalloc/flowra.ml`'s `Colorgraph.ralloc`, wired in at `-O3` for every
  backend), with move-coalescing already present (a prior session found
  and fixed unsound non-tmp/pseudo-register handling in that coalescing;
  native-x86-O3 is 66/66 as of this writing).

All of the above run per-backend, gated by `opt_level > 0`, invoked
identically from every `arch/*/​*backend.ml` (`Optimize.trim_unreachable_code`
unconditionally, then `simplify_exps` / `remove_nops` /
`collapse_branch_chains` / `elim_dead_assignments` / final `remove_nops` if
`opt_level > 0`) — see `driver/main.ml`'s `-O0`/`-O3` comment for the gating.

Verified: what's conspicuously missing
--------------------------------------------------------------------
- No common-subexpression elimination. `Availpass` computes available
  expressions already, but nothing in `opti/` uses that fact to *eliminate*
  a redundant recomputation — `Peephole.subst_forward` only substitutes a
  known value in order to re-fold it, not to skip recomputing a shared
  subexpression.
- No global/sparse constant propagation. `simplify_exps` is purely local
  (per-RTL); there is no dataflow-driven propagation of constants across
  block boundaries.
- ~~No loop/dominator analysis anywhere in the integrated tree.~~ Done as
  of 2026-08-17: `TODO/dominator.nw` -> `cfg/dataflow/dominator.ml`
  (Lengauer-Tarjan, ported to the current `Zipcfg` — the `.nw` predated
  the fork's reorg and didn't compile as tangled; three real bugs fixed
  along the way, see the file's own `claude:` comments) plus a new
  `Dominator.Query` layer (not part of the `.nw`) giving `dominates`/
  natural-loop/preheader queries a consumer actually wants, instead of
  the raw dominator tree `ZipGraph.translate` builds.
- ~~No loop-invariant code motion, no strength reduction~~ Done as of
  2026-08-17, both narrowly scoped (see their own header comments for the
  exact conditions each requires — deliberately conservative, not full
  textbook LICM/induction-variable analysis): `opti/licm.ml`
  (`Licm.hoist_invariants`) and `opti/strength_reduction.ml`
  (`Strength_reduction.reduce`), sharing `opti/loopopt.ml`'s block-editing
  helpers, both built on `Dominator.Query.loops`, wired into `~opt_level`
  in both `arch/x86/x86backend.ml` and `arch/ppc/ppcbackend.ml`. Showcased
  in `tests/optimizer/licm.c--` / `strength_reduction.c--`; full corpus
  re-verified clean at -O3 (`native-x86-O3` 66/66, `native-ppc-O3` matches
  its pre-existing baseline). No induction-variable analysis beyond
  strength reduction's own narrow one (a general IV pass is still a gap).
- No inlining anywhere in the pipeline — no call-graph representation
  exists at all currently.
- No SSA — see notes_ssa.txt; a deliberate, separate architectural choice,
  not a gap.

Proposed priority order (cheapest-given-existing-infra first)
--------------------------------------------------------------------
1. ~~**CSE (common-subexpression elimination).**~~ Implemented as of
   2026-08-18 (`opti/cse.ml`, `Cse.eliminate`) but **not wired into either
   backend** — it trips a real, pre-existing register-allocator hang in
   `Colorgraph.ralloc`, verified to be a different mechanism than the
   already-fixed loop-carried-value case. See
   `notes_colorgraph_spillcost.txt` for the full investigation, options,
   and how to re-enable it once fixed. (Turned out to need more new
   analysis than expected too: `Availpass`'s existing scaffolding hangs
   when driven this pass's way — see `opti/cse.ml`'s own header comment —
   so this ended up as a from-scratch local, single-block scan instead of
   a new client of the existing whole-procedure analysis.)
2. **Global/sparse constant propagation.** Same pattern as #1 — a new
   client of the existing `Dataflow.F` functor, analogous to how
   `Availpass` is built, propagating known-constant values across blocks
   instead of only folding within one RTL.
3. ~~**Bring up `TODO/dominator.nw`.**~~ Done — see above.
4. ~~**Loop-invariant code motion / strength reduction**~~ Done — see
   above. Still open: loop-aware spill-cost weighting in
   `Colorgraph.ralloc` (loop-nesting depth still isn't part of the spill
   heuristic) — `Dominator.Query.loops` is now available for that too,
   just not used there yet.
5. **Inlining.** Likely the single biggest win for small Tiger-style leaf
   procedures (the actual client, per CLAUDE.md's "goal" section), but a
   different layer of the compiler — it wants to happen earlier, around
   `Ast2ir`/call sites, not in `opti/`, and needs call-graph info that
   doesn't exist anywhere yet. Bigger design lift than 1-4.
6. **Target-specific peephole/strength-reduction patterns** (e.g.
   multiply/divide-by-constant-power-of-2 -> shifts). Lives in each
   `arch/*/​*rec.mlb`, not `opti/`. Long tail of small, backend-local wins
   rather than one big cross-backend one — lowest priority of this list,
   but cheap to pick off backend by backend once 1-2 land.

Why this order, tied to the fork's stated priorities: CLAUDE.md's "goal"
section explicitly favors simplification and end-to-end correctness over
optimization sophistication, and reusing dataflow machinery that already
exists (#1, #2) fits that better than standing up new infrastructure
(#3/#4) or a new compiler layer (#5) — do the cheap wins first.
