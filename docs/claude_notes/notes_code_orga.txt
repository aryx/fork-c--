Toplevel directory layout: grouping into clear, acyclic layers
================================================================

Written 2026-08-18, last updated same day against commit db5179c. Status:
mostly executed by hand (pad did the actual `git mv`s and dune edits as we
went, not Claude) - see "Execution status" below for exactly what's done vs.
still proposed. Re-verify this note's claims about `(libraries ...)` edges
before relying on them if much time has passed - directories keep moving in
this repo.

Relation to plan_reorg.md (now deleted)
----------------------------------------
plan_reorg.md (written 2026-08-05, executed 2026-08-06) took the tree from
the `front_*` naming scheme to a flat layout: `ir/`, `cfg/`, `elab/`,
`target/`, `codegen/`, `layout/`, `asm/`, `arch/`, `parsing/`, `error/`, plus
`todo/`'s eventual landing spots. Its postmortem section is worth
remembering even after deletion: the only thing that actually constrains
where a module can live is *what it depends on*, not what kind of thing it
is (data structure vs. pass vs. helper) - three rows of its own proposed
table turned out to be wrong for exactly that reason. The same lesson bit
again in this round (see the elab/ir ordering mistake below).

By the time this note started, the tree had moved further by hand: `ast/`
was split out of `parsing/`; `commons2/`/`commons3/` became `libs/prelude/`
and `libs/bitops/` rather than merging into one `commons/`; `opt/` and
`regalloc/` (from `todo/`) landed as `opti/` and `regalloc/`; a standalone
`analysis/` never materialized - `todo/dataflow/*` folded into
`cfg/dataflow/` instead.

The rule: no cycles across toplevel groups
--------------------------------------------
A grouping is only valid if, once you replace "which specific library" with
"which toplevel group", the dependency graph between groups stays acyclic.
This caught a real mistake mid-design: an early proposal put `regalloc/` in
a `middle/` group and `asm/`+`target/`+`arch/` in a `backend/` group. But
`regalloc/dune` lists `cmm_assembler` (asm/) as a dependency, and
`asm/dune` lists `cmm_front_ir` (codegen/, in `middle/`) - so `middle/` ->
`backend/` (via regalloc -> asm) and `backend/` -> `middle/` (via asm ->
codegen) at the same time. Moving `regalloc/` into `backend/` fixed it.

A second mistake of the same shape, later: an early draft lumped `ast/`,
`parsing/`, `elab/`, `rtl/` together as one flat "layer", with `ir/`
(now `fenv/`) one layer above. But `elab/dune` lists `cmm_ir` directly -
`elab/` actually sits *above* `fenv/`, not beside `ast/`/`rtl/`. Both
mistakes trace to the same root cause: presenting a DAG as a numbered stack
hides real branching and makes ordering errors easy to miss. Below, the
graph is a dependency table and a drawing, never a flat numbered list.

Dependency table (direct edges only, `libs/`+`error/` omitted - everything
depends on both)
------------------------------------------------------------------------
```
ast/              (leaf)
rtl/              -> ast/  (Rtlutil.ToAST: converts Rtl back to Ast, used by
                             asm/astasm.ml to print assembly as C-- text)
parsing/          -> ast/
fenv/             -> rtl/                                   (was ir/)
elab/             -> fenv/  (+ ast/, currently transitive via parsing/)
cfg/legacy        -> fenv/                                  (was front_cfg)
cfg/zipcfg        -> cfg/legacy                              (was front_zipcfg)
cfg/dataflow      -> cfg/legacy, cfg/zipcfg
target/           -> fenv/, elab/, cfg/legacy
codegen/          -> fenv/, cfg/*, elab/, target/
opti/             -> codegen/, cfg/*, target/, elab/
layout/           -> codegen/, cfg/*, target/, elab/
asm/              -> codegen/, target/, cfg/*
regalloc/         -> opti/, layout/, asm/, codegen/, target/, elab/, cfg/*
arch/*            -> regalloc/, asm/, layout/, opti/, codegen/, target/,
                      cfg/*, elab/, fenv/  (+ h_camlburg for instr. selection)
driver/           -> arch/* (+ everything transitively)
```
Inside `codegen/`, `context.ml`/`talloc.ml` moved out of `fenv/` into it
(see "Why context/talloc left fenv/" below) - not shown as a separate row
since it's still one library today. If the `proc/`/`translate/`/`expand/`
split (also below) happens, `codegen/proc/` becomes the thing `translate/`
and `expand/` each depend on.

Why no toplevel `front/` group
----------------------------------
The whole point of this repo (per CLAUDE.md's "What this is") is to *be the
backend* for fork-tiger. A toplevel `front/` sitting next to a toplevel
`backend/` reads as "this project has its own frontend", which contradicts
that framing and invites confusion about which "front" is meant. Shortening
the name doesn't fix it - the pairing with `backend/` is what causes the
reading. So `ast/`, `parsing/`, `elab/`, `rtl/` stay as four standalone
toplevel directories instead of being grouped and named.

(For the record: `parsing/` does belong logically with this cluster -
`parsing/dune` genuinely depends on `cmm_ast`, and `elab/nelab.ml` genuinely
uses `Ast.variance` etc. But nothing outside `parsing/` uses its own
`Scan`/`Parse`/`Parse_cmm` modules, even though several downstream dune
files list `cmm_parsing` as a dependency - grep found zero such uses.
`rtl/`'s case turned out not to be dead weight, just misdirected - see
below - and got fixed. `fenv/`, `elab/`, `cfg/legacy/`, `codegen/` still
list `cmm_parsing` unpruned - still worth checking each the same way,
don't assume they're all as harmless as `rtl/`'s turned out to be.)

Why `ir/` became `fenv/`, and why it doesn't hold "the IR"
------------------------------------------------------------------
The name `ir/` invites a specific, wrong assumption: that it holds the
program's intermediate representation. It never did. This compiler's actual
representations of the program each already live in their own
correctly-named directory: `Ast` (from `parsing/`, lives in `ast/`), `Rtl`
(the real register-transfer-list IR, lives in `rtl/`), `Zipcfg`/`Cfg` (the
graph wrapper around `Rtl`, lives in `cfg/`). `ir/` held none of them -
`Fenv` (the elaboration environment), `Asm` (the assembler interface),
`Block`/`Eqn`/`Rtleqn`/`Vfp` (stack-layout equations), `Metrics`.

How it got that name: the deleted plan_reorg.md's original table planned to
merge `front_rtl` (the actual IR) *together with* `front_asm` + `front_fenv`
into one directory called `ir/` - under that plan "ir/" meant "all the core
data structures", a broader sense of the word. But per that plan's own
postmortem, `front_rtl` ended up split out into its own `rtl/` instead of
being folded in. The leftover - `front_asm` + `front_fenv` - kept the name
"ir/" anyway, even after the one thing that justified calling it "IR" moved
out next door. `fenv/` is the honest name: it's what CLAUDE.md called this
directory before the `ir/` rename, and it's literally what's in there.

Why `context.ml`/`talloc.ml` left `fenv/` for `codegen/`
------------------------------------------------------------
Not everything that was in `ir/` is actually Fenv-related, so a blind
`ir/ -> fenv/` rename would have kept a smaller version of the same
misnomer problem. Checked directly: `fenv.mli`'s `env'` record only embeds
three things - `asm : 'proc Asm.assembler`, `base : Block.t`,
`metrics : Metrics.t`. `Block` pulls in `Rtleqn`+`Vfp` (which pulls in
`Eqn`) as its own implementation. So `asm`, `block`, `eqn`, `rtleqn`, `vfp`,
`metrics`, `fenv` itself - 7 files - really are Fenv or something Fenv's own
type transitively needs, and stayed in `fenv/`.

`context.ml`/`talloc.ml` are different: `context.mli` depends on `Talloc`,
not on `Fenv` - neither appears anywhere in `fenv.ml`/`fenv.mli`. Their real
consumers are `codegen/`'s own `Proc`/`Call`/`Contn`/`Expander`/
`Postexpander`/`Ast2ir` (by far the heaviest use), plus `layout/`,
`regalloc/`, and every `arch/*`. They're temp-name/compilation-context
vocabulary for codegen's data structures, not part of the Fenv environment -
they only ended up in `ir/` originally because they needed *a* low, early
home, the same way `Asm` did, not because they're Fenv-related. Moving them
into `codegen/` introduces zero new cross-toplevel edges: every consumer
(`layout/`, `regalloc/`, every `arch/*`, `codegen/` itself) already
depended on `codegen/` for other reasons.

Why `fenv/`, `cfg/`, and `target/` stay standalone (not folded into
middle/ or grouped with ast/parsing/elab/rtl/)
------------------------------------------------------------------------
All three are consulted symmetrically by many later stages rather than
being scoped to one:

- `fenv/` (Fenv, Asm interface, Block/Eqn/Metrics/Rtleqn/Vfp) is a direct
  dependency of `elab/`, `cfg/*`, `target/`, `codegen/`, `opti/`, `layout/`,
  `asm/`, `regalloc/`, and every `arch/*` - i.e. everything from
  elaboration onward, not just one stage. (`elab/` itself depends on it too
  - see the dependency table above - which is also why `fenv/` cannot be
  grouped with `ast/`/`parsing/`/`elab/`/`rtl/`: those four aren't a clean
  layer below `fenv/`, `elab/` is above it.)
- `target/` (`Target.t`, `Automaton` calling-convention specs) is a direct
  dependency of every single library in both `middle/` and `backend/`
  (checked all six: codegen, opti, layout, asm, regalloc, arch/x86 all list
  `cmm_front_target`). Folding it into either group would make the other
  group depend on it transitively for no reason, or - worse - introduce the
  same kind of cycle the regalloc/asm case did.
- `cfg/` is a shared foundation multiple later stages (`target/`,
  `codegen/`, `opti/`, `layout/`, `asm/`, `regalloc/`, `arch/*`) build on
  independently - not scoped to `middle/` or `backend/` alone either.

Why `cfg/front_cfg` -> `cfg/legacy`, `cfg/front_zipcfg` -> `cfg/zipcfg`
----------------------------------------------------------------------------
Dropping the `front_` prefix (a vestige of the old naming scheme, no longer
meaningful once the toplevel `cfg/` grouping already exists) hits a naming
collision for the older representation: its own primary module is literally
named `Cfg`, same as the parent directory, so `cfg/cfg/` was the natural but
confusing result. `cfg/legacy/` sidesteps it by naming the directory after
its role instead of its eponymous module - CLAUDE.md already calls it the
"older representation" and the deleted plan_reorg.md already described
merging it with the newer one under `cfg/` as making "eventually deleting
the old one a visible decision". `cfg/zipcfg/` keeps its own module name
directly, since `Zipcfg` doesn't collide with the parent.

One caveat worth keeping in mind: "legacy" describes design intent, not
current usage. Checked directly - `Cfg.` (the "legacy" one) is referenced by
143 files outside `cfg/`; `Zipcfg.` (the "current" one) by only 15. The old
representation is still the workhorse today; "legacy" signals where it's
headed, not how much it's used right now.

Why `layout/` is in `middle/`, not `backend/`
------------------------------------------------
It's tempting to think "frame layout" sounds like backend work. The actual
distinction that matters here: does a pass commit to a *real* machine
register or emit *real* output, or does it only ever rewrite the abstract
RTL/CFG representation?

- `middle/` (codegen/, opti/, layout/): `codegen/` lowers AST to RTL
  procedures still using pseudo-registers; `opti/` runs dataflow
  optimizations over that CFG; `layout/` solves the stack-frame equations
  (Placevar, Vfp, Framelayout, Mvalidate) and rewrites RTLs to reference
  offsets from a *virtual* frame pointer - still symbolic. None of their
  three `dune` files list `cmm_assembler` or `cmm_regalloc`.
- `backend/` (asm/, regalloc/, arch/): `regalloc/` replaces pseudo-registers
  with real machine registers - and needs `cmm_assembler` specifically
  because spilling means emitting real load/store instructions through the
  `Asm` interface, which is exactly why `regalloc/dune` lists it. `asm/`
  implements `Asm.assembler` - i.e. produces concrete output. `arch/` plugs
  in one machine's real register set, calling convention, and instruction
  selection.

So the dividing line is "committed to a real register or real emitted
output" vs. "still abstract", not "sounds like backend work".

Why `arch/` nests inside `backend/` rather than staying a toplevel peer
----------------------------------------------------------------------------
`arch/` is a different *kind* of directory from everything else here: every
other toplevel entry is one shared library, while `arch/` is ~10 per-target
implementations (x86, ppc, mips, arm, riscv32, riscv64, sparc, alpha,
dummy, interpreter) that each *consume* `asm/`+`regalloc/`+`target/`'s
generic interfaces (confirmed via `arch/x86/dune`: it lists `cmm_regalloc`,
`cmm_assembler`, `cmm_front_last`, `cmm_opti`, `cmm_front_ir` - i.e.
everything in both `middle/` and the rest of `backend/`). Nesting it as
`backend/arch/x86/` etc., rather than pulling it out to toplevel, gets two
things at once: it reads as "arch is backend work" (true, and useful to see
at a glance), and the "different kind of directory" distinction is just
naturally expressed as a subdirectory of subdirectories - the same pattern
`cfg/` already established by holding `legacy/`, `zipcfg/`, and
`dataflow/` as three subdirs side by side.

Splitting `codegen/` further: `proc/`, `translate/`, `expand/` (proposed,
not yet executed)
------------------------------------------------------------------------
`codegen/` has 15 modules today (30 files) - genuinely a lot for one flat
directory, and unlike `fenv/`'s files, they split cleanly along a real fault
line, mapped the same way as `fenv/`'s internal references were:

```
proc/       proc, call, contn, preast2ir, automatongraph, context, talloc
              (leaf-ish; the shared procedure/naming vocabulary)
translate/  ast2ir, widen, idcode, runtimedata
              -> only depends on proc/
expand/     expander, postexpander, rewrite, opshape
              -> only depends on proc/
```
`translate/` (Ast -> procedures) and `expand/` (procedures -> machine-
dependent RTL, run later per-target) never reference each other's modules
at all - both are independent consumers of `proc/`, the same shape as
`codegen/`/`opti/`/`layout/` one level up. Not a new idea either - CLAUDE.md's
own line for this directory already separates these three concerns in prose
("`Ast2ir.translate`... `Expander`/`Postexpander`... `Call`, `Contn`, `Proc`,
`Talloc`, `Runtimedata`").

`proc/` is named after its own eponymous type (`Proc.t`, the procedure
representation) the same way `cfg/legacy/` is named after `Cfg` - everything
else in the cluster is in direct service of it (`Call`/`Contn` for calling
into and continuing within a procedure, `Context`/`Talloc` for naming state
scoped to building one, `Preast2ir` for preprocessing before building one,
`Automatongraph` as a debug printer for the calling-convention automata
`Call` uses).

Two ways to realize the split, different cost:
1. Subdirectories only, `(include_subdirs unqualified)`, keep one
   `cmm_front_ir` library - zero edits outside `codegen/`, but no
   precedent for `include_subdirs` anywhere in this repo.
2. Three separate libraries, matching how `cfg/` already does exactly this.
   Consistent with the one precedent already set. Cost: 16 `dune` files
   currently list `cmm_front_ir` (`backend/asm`, `backend/regalloc`,
   `middle/layout`, `middle/opti`, `driver`, all 10 `arch/*`) and would need
   the new names instead (`cmm_codegen_proc`, `cmm_codegen_translate`,
   `cmm_codegen_expand`, matching the `cmm_cfg_dataflow` precedent for a
   freshly-split-out name). First pass: have all 16 depend on all three
   uniformly rather than working out which subset each actually needs -
   that finer split is a worthwhile follow-up, not a blocker.
Leaning toward option 2 for consistency with `cfg/`'s existing precedent.

Naming convention: directories named after their own data structure
------------------------------------------------------------------------
`ast/`, `rtl/`, `fenv/`, `cfg/`, `proc/` (if the split above happens), and
`target/` all share a pattern: each is named after the one dominant,
broadly-reused type it owns (`Ast.program`, `Rtl.rtl`, `Fenv.env`,
`Cfg`/`Zipcfg`, `Proc.t`, `Target.t`), with closely-related supporting
vocabulary alongside it in the same directory.

Checked whether anything is missing this treatment. Two candidates, neither
panned out:
- `target/` already fits - it just wasn't part of the active renaming
  discussion since it was never misnamed.
- `elab/` is the odd one out in this list - it's named after the *process*
  (elaboration), not a data structure. Its data structure is `Nast`
  (`elab/nast.ml`) plus `Nelab.compunit`, and both are correctly scoped as
  private to `elab/`: outside it, `Nast` is only touched by `driver/`
  (which touches everything, so that doesn't count), and `Nelab.compunit`
  only by `driver/`, `target/`'s one `tx_ast` hook field, and `codegen/`'s
  translation entry point - nothing like `Ast`/`Rtl`/`Fenv`/`Proc`/`Cfg`'s
  dozens of consumers each. Not a gap - `elab/`, `translate/`, `expand/`,
  `opti/`, `layout/`, `regalloc/`, `asm/`, `arch/`, `parsing/`, `driver/`
  are legitimately process/pass/entry-point directories, a different and
  equally valid category from the data-structure-named ones above.

Mechanics
------------
- `git mv` each directory into place.
- `sed` the `<<dir/file>>` chunk names in `docs/literate/Cmm.nw` and
  `docs/literate/Cmm_extra.nw` (definitions and uses share the same prefix,
  so one substitution per directory covers both).
- Update `SRC_VIEWS` in `docs/literate/mkfile` the same way.
- Run `dune build` then `make sync` immediately after each move, before
  anything else lands on top - `.md5sum_*` files travel with `git mv`
  (keyed on content), but confirm rather than assume.
- Renaming a `dune` library's `(name cmm_...)` field and every
  `(libraries ...)` mentioning it is optional and separable from the
  directory move itself - dune doesn't care about path/name
  correspondence. Deferred on purpose both this round and the previous
  reorg; still on the table as a follow-up cleanup.
- The legacy top-level `Makefile`'s `MAKESUBDIRS`/`INCLUDEDIRS` and each
  moved directory's own per-dir `Makefile` (`TOP=..`-style relative paths)
  are already stale from the *previous* reorg (still list pre-2026-08-06
  `front_*` names) and `opti/`/`regalloc/` never even got their own legacy
  `Makefile`s. Not worth fixing as part of this move unless you actually
  plan to use `make allold` - dune is the maintained build path
  (see CLAUDE.md).
