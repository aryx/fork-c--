Bringing up a 64-bit backend end to end: what actually blocks it
==================================================================

Written 2026-08-17, against the commit that added tests/tiger64/ and
runtime/qc--runtime.h's Cmm_Word fix. Verified claims below were read in
the code or observed by running qc; re-verify file:line references before
acting on them, they rot fast.

Context: this fork has two 64-bit backends, -alpha and -riscv64. Both
compile simple, allocation-free programs fine (demos/hello_alpha.c--,
demos/hello_riscv64.c--, both verified under qemu). Neither could run a
real Tiger program - i.e. anything that allocates on the heap and
triggers a garbage collection - until this session, which got -riscv64 to
13/15 against fork-tiger's test suite (tests/tiger64/, see that
directory's own README for the exact bring-up and the two bugs still
open). This note is the target-independent summary: what generalizes to
-alpha or any future 64-bit backend, versus what is riscv64-specific (see
docs/claude_notes/notes_riscv.txt for that).

The three places "64-bit" has to be threaded through
-------------------------------------------------------
Getting a 64-bit Tiger program to run touches three independently-owned
pieces of code, each of which had its own bits32-hardcoding bug:

1. fork-tiger's tigerc -64 flag (fork-tiger repo, frontend/frame.ml,
   backend/codegen.ml) - emits bits64 C-- for a Tiger *program*. Two bugs
   here made its own output invalid C-- under a bits64 target (a GC
   descriptor table literal defaulting to native word size instead of its
   declared bits32; a boolean-widen hardcoded to %sx32) - fixed in
   fork-tiger, see that repo's git log.

2. fork-tiger's own hand-written runtime (fork-tiger repo, runtime/gc.c,
   stdlib/stdlib.c, stdlib/stdlib.h) - NOT generated by tigerc, written
   once and shared across every backend. Hardcoded "unsigned" (always 32
   bits) for heap pointers and the allocation header - this is what
   "fork-tiger's runtime hardcoding bits32 pointers" meant in earlier
   session notes/memory about alpha being blocked. Ported to uintptr_t in
   fork-tiger (a no-op on 32-bit backends, confirmed by rerunning every
   other backend's own tests/run-tiger-*.sh afterwards and matching their
   recorded baselines exactly). The .c-- side of this same file's own
   32-bit hardcoding (bits32 literals, a "+4" header-skip offset, a
   0xFFFFFFFC alignment mask) has no such easy fix - the .c-- text itself
   has to change - so that transform lives in fork-c--'s
   tests/tiger64/regenerate-riscv64.sh instead of being checked into
   fork-tiger, mirroring how tests/tiger/regenerate-ppc.sh keeps its own
   byteorder-flip transform out of fork-tiger too.

3. qc-- itself (this repo, runtime/qc--runtime.h, runtime/pcmap.c) - the
   one that actually generalizes to EVERY 64-bit backend, not just
   fork-tiger's client code. Cmm_Word, the type backing every
   pc_map_entry field (register/stack-slot locations, the
   return-address location, span values, register/local/span counts)
   AND the actual register/stack-pointer VALUES the GC's own
   activation-record walk reads through it, was hardcoded "unsigned" (32
   bits) - for every backend, unconditionally. This was never caught
   before because every backend prior to this session's -riscv64 work
   was 32-bit, where "unsigned" and "native pointer width" are the same
   size by coincidence. qc-- itself already emits every one of these
   fields at the target's actual pointer width (verified from a
   -riscv64 .s dump: inalloc/outalloc/return_addressp/num_registers/etc.
   are all ".dword", not ".long", and the MKOFFSET(0) sentinel shows up
   as bit 63 set, not bit 31) - so on a 64-bit target the C runtime was
   reading its own pcmap data at the wrong stride/width, corrupting the
   very first activation-record walk any real GC cycle ever performed
   under a 64-bit backend. Fixed by retyping Cmm_Word to uintptr_t
   (qc--runtime.h) and widening pcmap.c's Cmm_loctype/Cmm_as_register/
   Cmm_as_offset decoding to match (their GOODBITS macro already derives
   from sizeof() of their own local variable, so this generalized for
   free once that variable's type did) - a no-op on 32-bit backends,
   confirmed the same way as item 2. This is target-generic runtime code,
   untouched by anything riscv64-specific, so it is very likely also why
   alpha's own tiger tests were blocked - on top of, not instead of,
   alpha's separate instruction-selection gaps (see below).

Item 3 is the one worth remembering if a future 64-bit backend (or a
revisit of alpha) hits the same class of symptom: every test that
allocates enough to ever collect crashing or heap-corrupting,
unconditionally, the first time the GC actually runs, while simple
allocation-free demos work fine. That symptom fingerprint means "the
runtime is misreading its own pcmap data's width", not a codegen bug in
the backend's instruction selection.

What's still backend-specific (not fixed by any of the above)
------------------------------------------------------------------
-alpha does not codegen real Tiger programs at all yet, independent of
runtime correctness:
  - alloc_one: no registers to spill (even on hello) - alpha's register
    allocator/spiller can't handle these frames.
  - "No acceptable widths for %mul/%quot on target 'alpha'; asked for
    64->64->64" - alpha's instruction selection only has 32-bit mul/quot.
-riscv64 had the analogous gap (no %quot at all, not just wrong width)
before this session - see notes_riscv.txt item 3 for that fix, since it's
riscv64-specific machinery (riscv64rec.mlb).

Two more, narrower bugs remain open in tests/tiger64/ against -riscv64
even with all of the above fixed - see tests/tiger64/README for the full
detail:
  - colmajor: real heap corruption ("malloc(): corrupted top size"), but
    only at the default heap size and only once a real GC cycle runs
    (confirmed correct with a huge heap) - root cause not yet found.
  - merge: correct stdout, wrong exit code (0 instead of 1) - not a GC
    bug (confirmed independent of heap size); leading suspect is a
    calling-convention/tail-call return-value bug in the recursive
    printlist chain that computes the program's final return value.
