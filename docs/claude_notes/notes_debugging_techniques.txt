Debugging techniques, written up as they get used
=================================================

Notes on *how* bugs in this compiler were found, as opposed to what they
were. Each entry names the technique, the bug it found, and - where it
applies - the mistake that made it take longer than it should have.

Started 2026-08-11 while chasing "Cmm_YoungestActivation: Assertion `entry'
failed", which broke 12 of the 15 tiger tests.


1. Read the assertion, then read the code around it
---------------------------------------------------
The message named a file and a line: runtime.c:144. Two minutes of reading
gave the whole shape of the problem:

    pc_map_entry* entry = Cmm_lookup_entry(k->pc);
    assert(entry);

so: something looks up a program counter in a table, and does not find it.
That immediately splits into three candidates - the table is empty, the
table is wrong, or the pc is wrong - and the rest of the session was
deciding which.

Worth doing before any tooling. It converts "the tests fail" into three
falsifiable statements.


2. Look for the program's own instrumentation before writing your own
----------------------------------------------------------------------
pcmap.c already had

    char *debug = getenv("QCDEBUG");
    if (debug && strstr(debug, "pcmap")) ...

Old C code is often full of this. It costs nothing to check and it is
written by someone who understood the data structure. Here it also told us
something by *not* firing: the "PCMAP array is unsorted!" warning never
appeared, which ruled out a whole class of explanation (binary search on
unsorted data) without an experiment.


3. Follow the data, and separate "in the file" from "in memory"
----------------------------------------------------------------
This is the one that actually cracked it.

The table lives in a section the compiler emits. So:

    # what does the compiler emit?
    grep -c pcmap build/hello.s

    # did it survive into the object?
    i686-linux-gnu-readelf -S build/tiger/sieve.o | grep pcmap

    # and into the executable?
    i686-linux-gnu-nm sieve | grep Cmm_pc_map
    i686-linux-gnu-objdump -s -j .rodata \
        --start-address=0x080f4f28 --stop-address=0x080f5048 sieve

The first answer was "zero" - the compiler emitted no pcmap at all, because
the *emit_data phase had never been ported from the Lua. Fixing that gave a
table that looked perfect in the executable: ascending return addresses,
each paired with a descriptor.

And yet at run time every entry read as zero.

That gap - correct in the file, zero in memory - has a small number of
causes, and the tool that distinguishes them is readelf:

    i686-linux-gnu-readelf -S sieve | grep rodata
      [ 8] .rodata  PROGBITS  080ba000  01cbdc  A     <- allocated
      [21] .rodata  PROGBITS  080f4f28  000c64        <- NO 'A' flag

    i686-linux-gnu-readelf -l sieve | grep LOAD       <- no segment covers it

An ELF section without the ALLOC flag exists in the file and is never mapped
into memory. Reads of it return whatever happens to be at that address,
which was zero.

Generalisation: when data is provably correct on disk but wrong at run time,
stop looking at the producer and check whether the thing is *loaded* -
section flags, program headers, and whether the address falls inside a
PT_LOAD range.


4. Believe the toolchain's warnings
------------------------------------
Every link had been printing

    ld: warning: pcmap.ld contains output sections; did you forget -T?

and it had been filtered out of the test output as noise for most of a day.
It is precisely the diagnosis: a linker script containing SECTIONS, passed
as an ordinary input file rather than with -T, gets appended to the default
script instead of merged into it - which is how a second, non-allocated
.rodata came to exist.

A warning that appears on every single link is easy to stop seeing. Grep
your own filters occasionally for what you have taught yourself to ignore.


5. Compare against a known-good artefact to date the bug
---------------------------------------------------------
Before changing the emitter it was worth knowing whether we had broken
something or inherited it. tests/tiger/ ships objects built by upstream
qc-- twenty years ago, so:

    readelf -S build/tiger/sieve.o     | grep pcmap   # ours
    readelf -S tiger/tigermain-x86.o   | grep pcmap   # upstream's

Both lacked the ALLOC flag. So this was never a regression: the 2004 linker
merged such a script into the real .rodata, and a modern one does not. That
changed the fix from "restore what we broke" to "emit what a modern linker
needs", and it is a different patch.

Having a known-good artefact of any kind - an old binary, a release
tarball, another implementation - is worth a lot. Look for one before
concluding that you caused a bug.


6. Get the value *and* its context, by print or by debugger
------------------------------------------------------------
Static inspection eventually runs out and you have to look at the running
program. Two ways, and the choice matters less than the habit of capturing
context alongside the value.

A temporary fprintf is fine when the code is yours. What made it useful here
was printing the failing pc *together with* the table it was searched in:

    DEBUG lookup FAILED for pc=0x804b334; map has 36 entries [0x80f4f28..0x80f5048)
      ra[0] = (nil)
      ra[1] = (nil)

"Not found" alone suggests the pc is wrong. The table alongside it showed the
table was wrong, which is a different bug. One line of context turned a wrong
hypothesis into the right one.

Prefer a debugger when the code is not yours - here gc.c belongs to
fork-tiger and runtime/*.c is generated from a .nw, so editing either to add
a printf is friction you do not need. See entry 10 for the cross-architecture
mechanics.

Whichever you use: remove the instrumentation before measuring the final
state, and rebuild everything that embeds it. A stale
runtime/build/libqcmm.a briefly made a real fix look like no change at all.

7. Attribute an address to a symbol
------------------------------------
Once the table was correct the lookup still failed, now for pc=0x804d98b.
Whose code is that?

    i686-linux-gnu-nm -n sieve | awk '$1<="0804d98b"' | tail -3
    ...
    0804d920 t __libc_start_call_main

nm -n sorts by address, so the last symbol at or below the target is the
one containing it. The answer - libc - reframed the question completely:
the stack walk was running past the outermost C-- frame, which is a
different bug from anything to do with the table.

addr2line is the nicer tool when the binary has debug info; nm -n works
without it.


8. Watch the failure *mode*, not just pass/fail
------------------------------------------------
After the ALLOC fix the eleven still-failing tests stopped asserting and
started segfaulting. That looks like no progress on a pass/fail chart and is
in fact good news: the assertion is gone, so the lookup now succeeds and
execution proceeds further before dying. A changed failure mode is evidence,
and a test suite that only records PASS/FAIL will hide it. Read the stderr.


9. Change one thing, then re-measure against a baseline
--------------------------------------------------------
tests/run-tiger.sh compares against a recorded baseline rather than
demanding that everything pass, so a single-test improvement shows up as a
diff:

    CHANGED against the baseline ('<' expected, '>' got):
    < exceptions FAIL
    > exceptions PASS

That is how "the ALLOC fix bought us exception unwinding but not garbage
collection" became visible immediately, and it also names which subsystem
each remaining failure belongs to.


10. Debugging a foreign-architecture binary: qemu + gdb-multiarch
------------------------------------------------------------------
We compile 32-bit x86 on an aarch64 machine, so the binaries cannot be run
natively and gdb cannot debug them directly. qemu-user has a built-in gdb
stub, which makes this no harder than an ordinary session:

    # terminal 1 (or backgrounded): start the program, stopped, listening
    qemu-i386 -g 1234 ./build/tiger/sieve

    # terminal 2: attach
    gdb-multiarch -q ./build/tiger/sieve
      (gdb) set architecture i386
      (gdb) target remote :1234
      (gdb) continue

Scriptable in one line, which is what to do from an agent or a Makefile:

    (qemu-i386 -g 1234 ./sieve &) ; sleep 2
    gdb-multiarch -q -batch \
      -ex "set architecture i386" -ex "target remote :1234" \
      -ex continue -ex "bt 12" -ex "info registers eax ecx esp" \
      -ex "x/1i \$eip" ./sieve

"set architecture i386" before connecting matters: gdb otherwise guesses from
the host and the backtrace is nonsense.

What this bought here, in one run: the faulting frame
(Cmm_c_change_activation), the call chain that reached it (Cmm_ChangeActivation
<- tig_gc <- tig_call_gc, i.e. the garbage collector's stack walk), the
faulting instruction ("mov (%eax),%eax") and the bad value (eax = 0x1). That
is the whole diagnosis - a frame pointer of 1 being dereferenced - from
material no amount of static inspection would have produced.

Notes:
 - the binaries here are linked -static, so there are no shared-library
   symbol problems; expect "BFD: warning: system-supplied DSO ... corrupt
   string table index" and ignore it.
 - "Backtrace stopped: previous frame inner to this frame" at the boundary
   is expected: the frames below are C-- ones, which do not follow the C
   frame-pointer convention gdb assumes.
 - no debug info in these objects, so you get symbol names and registers but
   not source lines or locals. Enough, usually.

11. Eliminate hypotheses cheaply, and write down what you eliminated
---------------------------------------------------------------------
A hard bug is mostly a list of plausible causes being shortened. The
discipline that pays is picking, each time, the cheapest experiment that can
*falsify* something - and recording the negative results, because otherwise
they get re-tested a day later.

From the garbage-collector walk, in the order they were killed:

  "the 20-year-old prebuilt objects are incompatible"
      relinked the failing test against objects built entirely from source.
      Still segfaulted. One command, hypothesis dead.

  "qemu is lying to us"
      the bad value is produced by the runtime reading a location our own
      compiler recorded; qemu does not participate. And the exceptions test
      passes through the same emulator and the same machinery. Reasoned
      rather than tested - but note the free experiment banked for later:
      CI runs this suite on native amd64, so its result settles it.

  "we do not emit pcmap entries for every call site"
      counted call sites in the .s against entries in .pcmap. Equal.

  "our register numbering disagrees with the runtime's"
      decoded our descriptor (%ebp saved at vfp-16, index 9) and grepped the
      runtime (#define EBP 9). Agreed.

  "our descriptors are malformed"
      dumped upstream's prebuilt descriptor beside ours. Same field layout,
      same shape of values, including the negative ra offset that had looked
      wrong to me.

What survived is worth more for having a graveyard behind it: we save four
callee-saved registers where upstream saved one, and one of them is %ebp,
which the C-frame walker wants to be a frame pointer rather than an ordinary
saved register.

12. When the code is "correct", question the environment's assumptions
------------------------------------------------------------------------
The garbage-collector crash ended up not being a bug in this compiler at
all, and the thing that had kept it hidden was an assumption nobody had
written down.

The chain, once it was visible, was short. Cmm_change_activation looks the
return address up in the pcmap; if it is absent the caller must be C, so it
switches to the C walker (runtime.c:65). That is *correct* when the walk
reaches the outermost C-- frame, whose caller is libc. The C walker then
follows the %ebp frame-pointer chain - and that is the assumption:

    callerebp = *(Cmm_Word *)a->vfp;    /* a->vfp is a saved %ebp */

Modern glibc and crt are built with -fomit-frame-pointer and use %ebp as an
ordinary register. One gdb command settled it:

    (gdb) break main
    (gdb) info registers ebp
    ebp   0x1

libc hands main an %ebp of 1. Our C-- main dutifully saves that 1 as its
callee-saved %ebp, the walk recovers it at the boundary, dereferences it,
and dies. In 2004, when this runtime was written, glibc kept frame pointers
and the chain terminated at 0.

The fix was three lines in the C walker - treat a misaligned %ebp as the end
of the walk rather than a pointer - and took the tiger suite from 3 passing
to 14.

Two generalisations worth carrying:

 - When every artefact you produce looks right and the thing still breaks,
   start listing what the *surrounding system* is assumed to provide. Frame
   pointers, section flags, symbol visibility, alignment, a sorted array, a
   locale. Twenty-year-old code is a rich source of assumptions that were
   free when it was written and are not free now.

 - "Correct but for a different era" is a distinct category from "wrong",
   and it changes the fix. Here nothing in the compiler needed changing;
   the runtime needed to stop trusting a convention the platform no longer
   honours. Entry 5's known-good artefact is the sibling technique: it tells
   you whether *you* broke it. This one tells you whether anyone did.

13. Reading globals in a binary with no debug info
---------------------------------------------------
These objects carry no DWARF, so gdb cannot say "print heap_size". The
symbol table is still there, though, and that is enough:

    i686-linux-gnu-nm queens | grep -E " [bBdD] (heap_size|space_end)$"
      080f31fc b heap_size
      080f3210 B space_end

    (gdb) x/1dw 0x080f31fc     # as decimal
    (gdb) x/1xw 0x080f3210     # as hex

The lower-case letters in nm's output mean local (static) symbols, which is
how file-scope statics in C stay visible. Reading a global this way settled
in one step that the heap really was the size we had asked for and that
space_end was consistent with it - killing two hypotheses that would
otherwise have needed instrumentation.

The same trick reaches data the compiler itself emits: the C-- global area
is a symbol like any other, so

    A=$(nm queens | awk '/Cmm.global_area/{print "0x"$1}')
    (gdb) x/2xw $A

prints the program's global variables - here alloc_ptr, which showed the
allocation pointer sitting exactly at the start of the heap and so proved
the collector had not been triggered by running out of room.


14. An absurd argument is a better clue than the crash site
------------------------------------------------------------
The queens crash is inside memcpy, which tells you nothing by itself -
memcpy is never the bug. The useful part was the register holding its
length:

    => 0x8077326 <memcpy+70>: rep movsl %ds:(%esi),%es:(%edi)
    ecx  0x1e8482   2000002

Two million words is eight megabytes, which was exactly the heap size in
that run. An object claiming to be the size of the entire heap is not a
corrupted object - it is not an object at all, and something has treated a
non-object as one.

That reframes the search immediately: stop looking at the copy, start
looking at who decided this address was a live object. In a garbage
collector that means the root set, which here comes from the span and
pcmap data the compiler emits.

Generally: when a crash lands in a library routine, the arguments at the
crash site usually identify the caller's mistake faster than the backtrace
does, and a value that resembles a *system quantity* - a heap size, a page
size, a file length, -1 - is a strong hint about which quantity was
misread.

15. Re-test eliminated hypotheses after the ground moves
---------------------------------------------------------
Entry 11 recommends writing down what you eliminated. The complement: a
negative result is only valid against the system as it was when you took it.

"The prebuilt tiger objects are incompatible" was tested, found innocent,
and written down as such. It was tested *before* the frame-pointer fix,
when every garbage-collecting test crashed for an unrelated reason - so the
experiment could not have shown a difference whatever the answer. Retested
afterwards, the same hypothesis was correct: building tiger's support code
from source makes queens pass, because the prebuilt objects' .pcmap sections
carry no ALLOC flag and their entries never reach the loaded map.

The tell to watch for is an experiment whose outcome is dominated by a
failure you already know about. If every configuration crashes in the same
place for a known reason, no configuration is being tested. Park the
hypothesis rather than eliminating it, and re-run it once the known failure
is gone.


16. Two bugs can hide behind one symptom
------------------------------------------
After the change above, queens passed and colmajor - which had been passing -
started failing. The count stayed at 14 of 15, which on a summary line looks
like no progress and is in fact two separate defects being separated from
each other:

  with the prebuilt objects:  queens fails    (missing pcmap entries)
  with source-built objects:  colmajor fails  (a bad GC root)

Neither configuration passes everything, and no single change was going to.
The useful move is to pick the configuration that is *more correct* rather
than the one with the better score - source-built, here, since it has
complete pcmap data, uses one toolchain, and can be instrumented - and then
attack what remains with the noise removed.

Being able to instrument mattered immediately. With the prebuilt archive in
the link, editing tiger's gc.c had no effect at all, because the gc.o being
linked was a twenty-year-old binary. Half an hour went into wondering why
printfs did not appear. If your instrumentation produces no output, check
that the code you edited is the code being built.

17. Find the spec before deciding whose bug it is
---------------------------------------------------
colmajor's collector crash came down to a garbage-collector root - stack
slot 11 of tiger_main - holding the value from_space, the first byte of the
heap, where a real object pointer would be from_space+4. Two readings were
possible, and they point at different repositories:

  ours   - we emit the wrong location or the wrong value for that slot
  theirs - the slot is genuinely uninitialised and tiger says it is a root

The instrumentation said which slot and which flag; the generated C-- said
when it is written:

    41:   call_gc() also aborts ;         <- first collection
    57:   bits32[%add(fp, 44)] = Lgbl_70; <- slot 11 first written

So the slot is read as a root sixteen lines before anything is stored in it.
That still does not say who is wrong - it depends on what stackdata
promises. docs/spec/ has the language definition:

    labels and declarations appear in stackdata { ... }.
    No initial value can be provided.

which settles it: stackdata is uninitialised by definition, this compiler is
right not to touch it, and a root map that claims an uninitialised slot
holds a pointer is unsound. The bug is in the front end, and no change here
would be a fix - only a way of hiding it.

The general point: when a bug sits at the boundary between two components,
the specification of that boundary decides which side owns it, and reading
it is usually quicker than arguing from the code. Without it the tempting
move here would have been to zero stackdata in the compiler, which would
have made the test pass, cost every procedure a memset, and left the real
defect in place for the next front end to trip over.

The corollary is worth stating too: "make the test pass" and "fix the bug"
are different objectives, and when they diverge it is worth saying so out
loud rather than quietly choosing the first.

18. -backtrace plus OCAMLRUNPARAM=b turns "Impossible" into a call chain
-------------------------------------------------------------------------
This compiler's own "can't happen" exceptions (Impossible.impossible) print a
message but, by default, only the outermost few frames - main.ml's top-level
handler, not where the check actually fired. There is a real flag for it:

    qc -backtrace ...             # main.ml re-raises instead of swallowing
    OCAMLRUNPARAM=b qc -backtrace ...   # and OCaml prints the full trace

which turned

    This can't happen: Asked for temporary in space
      'general-purpose temporaries' with unsupported width 64

into the exact chain that produced it:

    Talloc.Single.for_space.(fun)                    ir/talloc.ml:29
    Expander.IntFloatAddr.alloc            (inlined)  codegen/expander.ml:144
    Expander.IntFloatAddr.expand.to_temp'             codegen/expander.ml:240
    Expander.IntFloatAddr.expand.to_temp              codegen/expander.ml:961
    Expander.IntFloatAddr.expand.to_temp'             codegen/expander.ml:285
    ...
    Expander.IntFloatAddr.expand.assign_room          codegen/expander.ml:888

Reading that bottom-to-top named the exact match arm (the "lobits of a
shifted wide temporary" case) and its caller (assign_room's "store into a
register" branch), which is what made the fix a five-line, targeted change
instead of a guess. Root's -g flag (already on for this whole build, see the
top-level dune's comment) is what makes this available at all; without debug
info the backtrace is empty frames.

Generalises past this project: any OCaml codebase with -g, check for a
"-backtrace"-style escape hatch (or just set OCAMLRUNPARAM=b and see what
happens) before reasoning from the exception message alone.


19. git log -p on the *upstream* file, not just the local one
----------------------------------------------------------------
Bare "<<" and ">>" (shift operators) had silently become invalid C-- syntax
- the lexer only accepted "@<<"/"@>>". Two hypotheses: this fork broke it
during the port, or upstream's own history explains the "@". The second one
only shows up by walking the *original* project's history, not this fork's:

    git -C ~/software-src/dev-toolchain/qc-- log -p --follow -- src/parser.nw \
      | awk '/^commit /{c=$2} /"<<"|"@<</{print c": "$0}'

which found the exact commit (f956c662, 2001) and, crucially, its message:
"Inserted the proper names into <<>>= chunks." That is a *noweb cleanup*
commit (naming anonymous chunks), not a language-design change - and noweb's
own chunk-reference syntax is literally "<<name>>", so a raw "<<" appearing
in program text needs escaping to survive a noweb-aware tool. The "@" was
never part of the C-- language; it was noweb punctuation that a modern
tangler (this fork's syncweb) failed to strip back out, and it has sat in
every build since.

Two things made this findable at all: having the *original* project checked
out locally (not just this fork), and reading the *message* of the
commit, not just its diff - the diff alone ("<<" -> "@<<") is equally
consistent with "the language changed" and "an escape leaked through", and
only the message disambiguates them.


20. Independent corpus files corroborate a hypothesis better than one
------------------------------------------------------------------------
The first read of the "<<" bug treated tests/cmm/tadd.c-- as a single buggy
fixture (three years newer than a syntax change, so plausibly just a stale
typo) and nearly got "fixed" by rewriting that one file to use backticks
instead. Before doing that:

    grep -rln '[^@]<<\|[^@]>>' tests/cmm/*.c-- demos/*.c--

found bare "<<"/">>" independently in const.c--, carry.c--, and err-002.c--
too - four unrelated files, written by different people at different times,
all assuming the same syntax works. One file being wrong could be a typo;
four independent files being wrong the same way is corpus-wide evidence that
the *lexer* is wrong, not the tests - which sent the investigation to
scan.mll instead, and was the actual bug (see entry 19).

When a "clearly broken" file turns out to be old, check whether anything
*else* in the corpus makes the same assumption before deciding the file is
the thing to fix.


21. Decompress and hand-trace the checked-in golden assembly
-----------------------------------------------------------------
tests/cmm/x86/*.s.gz are upstream's own compiled output from twenty years
ago - proof of what the compiler used to produce, not just what it was
supposed to. For the "bits64 on a 32-bit backend" investigation:

    gunzip -c tests/cmm/x86/r64.s.gz

and reading the whole function by hand (not skimming) showed the 64-bit
constant 0xfeedfacedeadbeef stored as two independent 32-bit immediate
stores to two adjacent stack addresses - never assembled into one register.
First pass through this trace concluded "no edx used, must all be memory"
and was wrong: a later, slower re-read found `movl %ecx,%edx` a few lines
down, meaning both eax *and* edx do end up holding the two halves at the
final `ret`. The correction mattered - it's what led to Automaton's
combine_loc (target/automaton.ml) as the real mechanism, rather than a
dead-end theory about a hidden-pointer return convention.

The general lesson is really two: (a) a golden binary artifact answers "did
this used to work, and how" more reliably than reading source, since source
tells you intent and the binary tells you what actually happened; (b) when
hand-tracing registers through a disassembly, check whether each one is
still live at the *last* instruction before concluding it was unused -
skimming for one keyword ("edx") without following where it goes is how the
first pass got it backwards.


22. The program's own debug hooks, again, for a different subsystem
------------------------------------------------------------------------
Entry 2 found pcmap.c's QCDEBUG hook. codegen/expander.ml has its own,
independent one - Debug.eprintf "expander" ..., gated by the same QCDEBUG
environment variable (error/debug.ml: `Str.split "," (Sys.getenv "QCDEBUG")`):

    QCDEBUG=expander qc -stop .s -o /tmp/out.s tests/cmm/float-003.c--

prints every expansion step, including the exact expression being pushed
onto the x87 stack right before the crash:

    Expanding bits64L[$V[0] + ...] := %f2f64(%f2f80(%pinf(), rm), rm)

which showed the widener had wrapped %pinf() in a *double* float-precision
conversion (f2f64(f2f80(...))) - not something visible from the source
(f = %pinf64;) or from the backtrace alone, which only named the match arm,
not the expression it was matching. Worth checking for a QCDEBUG word
*before* adding a temporary printf: `grep -rn 'Debug.on\|Debug.eprintf'` in
the module you're stuck in.


23. One missing pipeline stage causes lookalike bugs in unrelated places
-----------------------------------------------------------------------
Across one session, four crashes that looked unrelated -

  - %bool(...)/%false() reaching a conditional-guard expander unresolved
  - %round_down()/%round_nearest() reaching a "weird argument" slot unresolved
  - a %lobits(%shrl(<64-bit fetch>)) needing a temp wider than any register
  - %pinf()/%NaN64(...) reaching the postexpander as a live operator

all traced back to the same missing piece: Optimize.simplify_exps
(TODO/optimizers/optimize.nw), which upstream ran right before expansion and
this fork never wired in. elab/simplify.ml - the module that pass would have
called - already implements every one of these folds (bool, round_*, the
address-narrowing lobits/shrl-of-memory case, pinf/NaN-to-bit-pattern); they
just never got a chance to run on RTL built after elaboration (by widening,
by the calling-convention automaton).

Once the pattern was recognised, the question for each new "reached
postexpander" crash stopped being "what should this operator do" and became
"does elab/simplify.ml already do this, and why isn't it running here" -
usually a one-line check (`grep -n '"pinf"\|"round_down"\|...' elab/simplify.ml`)
that turned an open-ended implementation task into "call Simplify.exp (or
copy its rewrite) at the one unguarded call site."

Whether to fix this by wiring in the missing pass once, or by hardening each
call site that can be reached with unsimplified RTL, is itself a real
choice - this project chose the latter deliberately (see the commit
messages for these fixes), reasoning that correctness should not depend on
an optional optimization pass being plugged in, and that plugging the pass
in later should not regress anything that was made to work without it. That
is a defensible general default: an "optimization" whose absence causes a
crash rather than just worse code is not really optional, so either make it
mandatory infrastructure or make the code work without it - do not leave it
load-bearing while labelled optional.


24. Verify the minimal patch before reaching for the general fix
---------------------------------------------------------------------
tests/tiger/colmajor.c-- had one conditional branch whose then- and
else-arms both jumped to the same label (goto Lalc_gc_76 either way), which
looked like it could be a symptom of almost anything - a degenerate CFG the
backend mishandles, a register-allocator bug, anything. Before writing a
regenerate-from-source script, or chasing a "does the backend handle
identical branch targets" theory:

    python3 - <<'EOF'   # patch just that one line, nothing else
    ...
    EOF
    qc -globals ... && cc ... && qemu-i386 ./colmajor < input | diff - expected

Patching *only* the one suspicious line, with no other change, and getting a
clean pass proved the whole crash was that single corrupted label -
immediately ruling out every backend-side theory without needing to test any
of them. Only after that confirmation was it worth the larger, "more
correct" fix (regenerating from fork-tiger's real tigerc), because by then
the risk of that larger change hiding a different bug was gone.

The general shape: when a plausible one-line patch exists, apply *just* that
one and re-test before reaching for the systemic fix, even if the systemic
fix is what you intend to ship. It is the cheapest experiment available and
it tells you whether you are about to fix one bug or paper over two.


25. Attach gdb to qemu's gdbserver instead of reading a qemu -d in_asm trace
---------------------------------------------------------------------------
tests/run-native.sh BACKEND=ppc was segfaulting on most tests as soon as
it actually started compiling for ppc (see arch/ppc/ppc.ml's vregs/nvregs
fix). "qemu-ppc -d in_asm -D trace.log ./binary" dumps every instruction
executed, which for anything past a trivial program is thousands of lines
of raw opcodes with no register state - finding the fault in that requires
manually simulating the CPU by eye.

Instead: "qemu-ppc -g 1234 ./binary &", then
"gdb-multiarch -batch -ex 'set architecture powerpc:common' -ex 'target
remote :1234' -ex continue -ex bt -ex 'info registers' ./binary". This
runs the real target binary under qemu's own instruction-accurate
emulation (not a separate simulator) but gets a normal gdb session on top:
the exact faulting instruction, disassembly around it, and every register
at the moment of the crash, in seconds instead of a manual trace read.
gdb-multiarch was already installed; a target-specific
powerpc-linux-gnu-gdb was not, and was not needed - gdb-multiarch's
`set architecture` covers it.

This is what turned "qemu: uncaught target signal 11" into an actual
diagnosis: the faulting instruction was "lwz r11,-28680(r2)" *inside
glibc's own printf*, not in generated code at all - which is what pointed
at r2 being clobbered rather than at some code-generation mistake in the
printf call sequence itself. Reading a raw instruction trace would have
shown the same faulting address eventually, but not nearly as fast, and
without the "this is real libc code, so the bug is in what we handed it,
not in the call itself" framing that the backtrace + disassembly gave for
free.

A few refinements that came up reusing this same setup for later bugs
(hangs, not crashes - tests/cmm/tail.c--'s tail-recursive "down"):

- Break on the symbol name ("break down"), not a hand-computed address
  from objdump. An address copied from a *different* binary's
  disassembly (stale from an earlier iteration of the same investigation)
  is a real mistake to make under time pressure, and gdb resolves symbol
  names from the target's own symbol table regardless of ASLR/reloading,
  so there is no reason to compute addresses by hand at all.

- Always wrap *both* the backgrounded "qemu-ppc -g 1234 ..." and the gdb
  invocation in "timeout N". A breakpoint that is never hit (wrong
  address, wrong symbol, or the bug means that code path is never
  reached) leaves gdb's "continue" blocked forever, which without a
  wrapper hangs the whole shell command - and once that happens the qemu
  process is still running in the background afterward too, so
  "pkill -9 qemu-ppc" is worth doing before the next attempt.

- For a bug that only shows up after N iterations (not a crash, not
  reproducible on the first hit), don't single-step through everything -
  either loop "-ex continue -ex 'print $rN'" pairs (build the -ex list
  in a shell for loop, one pair per iteration, and grep the batch output
  for the "$N = ..." lines) to watch a register evolve iteration by
  iteration, or use "ignore <bpnum> <count>" to jump straight to a later
  hit and bisect from there. This is what separated "the stack pointer
  drifts by one frame every iteration" (visible checking every hit) from
  "arguments read back as garbage after ~20 iterations" (found by jumping
  ahead with ignore, then narrowing with the loop form once corruption
  was confirmed to exist somewhere in that range).

26. Bisecting which -O3 pass causes a bug: sed a pass to a no-op, don't
    comment it out by hand
---------------------------------------------------------------------------
tests/run-native.sh OPT=3 surfaced 5 failures with no suite-level clue
which of collapse_branch_chains/elim_dead_assignments/Peephole.subst_forward
(the three passes gated by opt_level in arch/x86/x86backend.ml's optimizer)
was responsible, or whether it took a combination. Isolating each
combination by hand-editing the file, rebuilding, testing, and reverting
for every one of 2^3 subsets would have been slow and error-prone (forgetting
to revert one is exactly how "make test-all is failing" happened mid-session
- see below).

The fast version: `cp` the file to /tmp first, then for each pass under
test, `sed -i` its `let proc = if opt_level > 0 then run X proc else proc in`
line to `let proc = proc in (* TEMP *)`, rebuild, run just the failing
tests by name (`OPT=3 ./run-native.sh bool multasgn taddov`, not the whole
suite), then `cp` the backup back before the next combination. This
isolated two *independent* bugs hiding behind one "5 failures" symptom
(entry 16, again) in about ten single-pass/pair-pass experiments:
collapse_branch_chains + elim_dead_assignments together break tail2/
tailnot, while Peephole.subst_forward alone (no interaction needed)
breaks bool/multasgn/taddov.

Once a single file is implicated, QCDEBUG dumps the pipeline already
defines are enough to see *where* it goes wrong without adding new
instrumentation - `env QCDEBUG=peephole ./bin/qc -O3 ...` traces every
substitution peephole considers and applies. But for a gap *between* two
existing QCDEBUG dump points (here: after Optimize.elim_dead_assignments,
which has no dump point of its own, and the final .s), the fastest path
was a *temporary* one-line `Debug.eprintf "instrsel-cfg" ...; Cfgutil.
print_cfg (fst proc)` spliced in right after the phase in question,
reusing an *existing* registered QCDEBUG word (instrsel-cfg was already
registered elsewhere in the same file) rather than adding a new
`Debug.register` call - one line to add, one line to `git checkout --`
away when done, no new permanent debug word to remember to remove.

Once the CFG dump pinpointed the bad RTL, reading the *final* assembly
directly (not the raw dataflow trace) was what actually cracked bool.c--'s
bug: `andl $1,%eax` computing a boolean test in place, clobbering %eax
before a later `movl %eax,4(%esp)` that still needed the original value
for a printf argument. The raw peephole trace (hundreds of "Considering"/
"Replacing" lines, many duplicated across dataflow fixpoint iterations)
was technically sufficient but far harder to read by eye than the ~15-line
final .s once the bug was narrowed to one function.

**The mid-session near-miss worth flagging explicitly**: after finishing
one isolation experiment, forgetting to restore the file before moving to
the next left arch/x86/x86backend.ml with several passes hard-disabled -
invisible until the user ran `make test-all` independently and saw
failures that had nothing to do with anything committed. `git diff
--stat`/`git status --short` immediately after every restore (not just
"I think I copied the backup back") would have caught this before it was
user-visible. Prefer `git checkout -- <file>` over restoring from a `cp`
backup when the file started clean (git is the more trustworthy source of
"clean"), and only reach for a `/tmp` backup when there's uncommitted work
in the file that a `git checkout` would discard.

27. A retry loop that never terminates: measure growth, don't just watch
    it spin
---------------------------------------------------------------------------
regalloc/colorgraph.ml's build -> ... -> selectSpill -> assignColors ->
resetProgram -> build retry loop hung on two different files, and looked
identical from the outside (both just spun, no crash, no progress
visible in the final output). Printf-tracing which register selectSpill
picked each round told them apart immediately:

- tests/cmm/add.c-- picked the exact same temp every round (thousands of
  identical "picked $t[5]" lines) - a *stuck* loop. The fix was finding
  what stale reference to that temp survived every rewrite attempt (see
  entry 16's sibling case: this took three wrong guesses -
  Call.cal_uses, then contedge defs/kills, before the real answer -
  Live.live_out_last reading a liveness property table that was
  populated once before the retry loop started and never re-solved as
  the loop rewrote the cfg round after round).

- tests/cmm/tail_from_c.c-- (isolated further to a minimal repro: any
  procedure with a *self-recursive tail call*, i.e. a real loop in the
  cfg, under enough register pressure to force a spill at all) picked a
  *different* temp every round, over 500 rounds without a single repeat.
  Same symptom (never terminates), different disease: not stuck, but
  diverging. Tracing "picked the same thing" would have found nothing
  here - the right measurement instead was |get_regs cfg| (the
  interference graph's own register count) printed at the top of each
  build(), which grew by exactly +1 every single round forever while
  |blocks| stayed constant. That pointed straight at the real mechanism:
  spilling a loop-carried value (live across the back-edge, e.g. a
  tail-recursive loop's own induction variables) inserts a reload whose
  live range *also* spans the loop, so it interferes with everything
  else alive there and needs spilling itself next round - and
  selectSpill's own cost heuristic (numUses / (liveRange * degree))
  keeps *choosing* loop-carried values because their liveRange is
  computed via a single linear pass over the cfg (not a fixed-point
  computation like the liveness analysis it borrows), undercounting
  exactly the "spans the back-edge" case that makes them the worst
  possible spill candidates.

The general lesson: "it never terminates" is not one bug shape. Before
hunting for a root cause, print something that grows (or doesn't) each
iteration - a chosen candidate's identity, a data structure's size,
anything cheap to measure - and let *that* shape (repeats vs. strictly
increasing, bounded vs. unbounded) decide which of "stuck" or
"diverging" you're actually chasing. They need entirely different
fixes, and guessing wrong wastes exactly the kind of time this entry is
trying to save.


28. Rebuild a stripped-of-debug-info library with -g just for the session
---------------------------------------------------------------------------
runtime/Makefile's CFLAGS32 never passes -g (entry 25 already notes "no
debug info in these objects, so you get symbol names and registers but
not source lines or locals"). That was a real limit chasing the ppc EBP
crash: gdb could name the frame (Cmm_init_c_frame) but not print `*a` or
`calleedata->num_registers` - exactly the values needed to tell "the
metadata table is empty" from "the metadata table has entries at
indices we're not checking."

    make BACKEND=ppc QC=.../bin/qc CFLAGS32="-g -w -fcommon -I ." clean
    make BACKEND=ppc QC=.../bin/qc CFLAGS32="-g -w -fcommon -I ."

is a one-line override, no Makefile edit needed since CFLAGS32 is already
a variable. Relink the specific failing test's .o against the resulting
build-ppc/libqcmm.a by hand (same objects run-tiger-ppc.sh would link,
just with -g added to the gcc invocation) rather than adding -g to the

entry 25's advice to remove instrumentation before measuring applies to

29. A struct-layout change needs every prebuilt consumer regenerated, not
    just the definer
---------------------------------------------------------------------------
Fixing qc--runtime.h's NUM_REGS (see entry 30) traded one crash for a
different one - "*** stack smashing detected ***" - which looked like a
*new*, worse bug. It was actually the *same* fix, half-applied: fork-tiger's
gc.c calls Cmm_YoungestActivation/Cmm_ChangeActivation directly, so it
must agree with runtime.c on the byte layout of `struct cmm_activation`.
tests/tiger/stdlib-ppc.a is a *checked-in prebuilt archive* (see
regenerate-ppc.sh's own header comment for why), built the last time
someone ran regenerate-ppc.sh against whatever qc--runtime.h existed then
- so after edit ing NUM_REGS, runtime.o (rebuilt fresh) and gc.o (still the
old archive) disagreed about sizeof(struct cmm_activation), and every
write through the new, bigger layout overran a stack-local Cmm_Activation
sized by the old one.

The fix was simply running the regeneration script that already existed
for exactly this (`tests/tiger/regenerate-ppc.sh`, which needs a
fork-tiger checkout - see its own comment for why the result is checked in
rather than rebuilt every test run) and confirming with `git status`
that stdlib-ppc.a actually changed.

General shape: when a shared struct/ABI type changes, grep for *every*
prebuilt artifact (archives, .o files, anything checked in rather than
built from the current source tree) that embeds assumptions about its
layout, not just the one file you edited - and watch the *failure mode*
(entry 8) for the tell: a struct-size mismatch often manifests as
corruption *downstream* of the real bug (here, a stack canary in a
totally different function) rather than anywhere near the type
definition itself.


30. Print the compiler's own internal numbering from a live process,
    don't just hand-derive it from source
---------------------------------------------------------------------------
gcc-linux.c hardcodes `#define EBP 9 /* r[5] */` - x86's activation-index
for the register the C-frame-walker trusts. Porting this to ppc required
knowing what index the *same* mechanism assigns to *some* ppc register,
and target/target.ml's mk_reg_ix_map (the code that assigns these
indices) is legible enough to hand-derive: sort register spaces
alphabetically by space character, concatenate each space's registers in
ascending order, number sequentially. Doing the arithmetic by hand
(c-space 8 entries -> 0-7, f-space 33 -> 8-40, r-space 33 -> 41-73, so
r31 -> 72) is exactly the kind of derivation entry 21 warns can go
subtly wrong under time pressure.

The check that actually mattered was empirical, not arithmetic: break at
Cmm_init_c_frame (needs entry 28's -g rebuild) and print the *data the
compiler itself emitted* for the specific procedure in question -

    (gdb) up
    (gdb) print calleedata->num_registers
    $1 = 18
    (gdb) print ((struct reg*)calleedata->data)[0]
    $2 = {index = 72, saved = {l = 4294967220}}
    ... (17 more, indices 55-72)

18 entries for indices 55-72 confirms both the hand-derived formula (r31
= 72, and ppc's nvregs really are r14-r31, 18 registers) *and*, more
importantly, that the mechanism (main unconditionally preserves every
nonvolatile register, regardless of whether its own body touches it -
ast2ir.ml's `RS.diff proc_cc.C.pre_nvregs proc_in'.C.regs`) actually
fires for this specific procedure. Reading the source answers "what
should happen"; printing the live pcmap entry answers "did it," and for
a hardcoded magic-number port like this one, only the second question
matters.

General shape: when hardcoding a value derived from a numbering scheme
the compiler itself assigns (register indices, layout offsets, hashes),
prefer dumping that scheme's *actual output* for a concrete case over
re-implementing its derivation by reading the assigning code - the
running program is always the ground truth, and a formula that's *nearly*
right (off-by-one in a sort order, a space classified differently than
expected) fails silently rather than loudly.


31. A gdb watchpoint expression is re-evaluated live - don't watch through
    a register that gets reused
---------------------------------------------------------------------------
Chasing colmajor.c--'s NULL-array-pointer crash (see entry 30's block_copy
bug), the first attempt to find *what* zeroed a specific outer-frame stack
slot was `watch *(int*)($r3+32)`, set right at a function's entry where r3
happened to hold the address of interest. It triggered - but on a value
and a call frame that made no sense, because r3 is an ordinary scratch/
argument register, reassigned dozens of times over the next few hundred
instructions. gdb re-evaluates a watchpoint's *expression* before every
check, not just its value at the moment `watch` was typed - so `$r3+32`
tracked wherever r3 pointed *at each instant*, not the fixed address it
happened to equal when the watchpoint was created.

The fix was mechanical: read the target address once as a concrete number
($1 = 0x407ff640), then `watch *(int*)0x407ff660` (arithmetic already
applied, no register in the expression at all). That immediately gave the
right instruction and the right backtrace.

Also needed along the way: `set can-use-hw-watchpoints 0` before `watch` -
qemu-ppc's gdbstub only offers so many hardware watchpoint slots, and this
session had already burned them on an earlier (bogus, register-based)
watchpoint left over from a prior attempt. A software watchpoint is slower
(gdb single-steps to check it) but has no such limit, and for a
single-shot investigation like this one the slowdown never mattered.

General shape: when a watchpoint result looks nonsensical (wrong frame,
wrong value, "this can't be where it changed"), suspect the *expression*
before the *hypothesis* - a watchpoint on `*(EXPR)` is only pinned to a
fixed address if EXPR itself is already a constant. Compute the address
once, watch the literal.


32. Scripted `stepi` with a `$pc` watchpoint to catch "control jumps
    somewhere nonsensical", when you don't know the faulting address
    up front
---------------------------------------------------------------------------
Bringing up the SPARC backend from scratch (no working upstream
reference to compare against, unlike ppc), demos/hello_sparc.c-- linked
and ran under qemu-sparc32plus but segfaulted with no output at all - not
even "hello, world!" - and the crashing PC read back as bare `0x0`, which
rules out a bad-but-plausible address (a wild pointer, an off-by-N) and
instead means control transferred through a register or memory slot that
held zero, i.e. something never got initialized or got overwritten with
zero at some point before the jump. There was no single address to
`break` on - the question was "where in the instruction stream does PC
become 0", not "what happens at a known bad instruction".

Same gdb-over-qemu-gdbserver setup as entry 25 (`qemu-sparc32plus -g 1234
./binary`, `gdb-multiarch ... target remote :1234`), but instead of
`continue` to a breakpoint, break once at a point already known to be
reached correctly (here, the callee's own entry - confirmed by checking
its arguments were sane first), then hand a Python loop to `-ex "python
<<script>>"`: `gdb.execute('stepi')` a few thousand times, reading
`$pc` after each step, and stop as soon as it equals 0 (or whatever the
known-bad value is), printing the step count and full register state
right there. This turns "single-step by hand and eyeball each line" -
impractical for anything past a dozen instructions - into an automated
scan that still gives an exact instruction-by-instruction trail, not just
the final crash site. The step count itself was also informative here:
it landed inside `__libc_start_call_main`, i.e. *after* the callee had
already returned once - which is what pointed at the return sequence,
not the call, as the actual bug (see below).

The underlying bug this found generalizes beyond SPARC: any target with
branch delay slots (SPARC, MIPS, and others) has TWO real conventions
that must agree with each other - (1) what value a `call`-class
instruction actually writes into the return-address register (SPARC
hardware writes the call instruction's *own* address, not the delay
slot's), and (2) what offset the `return`-class instruction adds back on
the way out (SPARC's real `ret`/`return` pseudo-ops add +8, precisely to
skip both the call and its delay slot). A backend's RTL model is free to
represent the stored value as `pc+4` instead of `pc` for uniformity with
non-delay-slot targets (matching how every other backend's generic "pc"
already means "address of the next sequential instruction") - but every
consumer of that value then has to agree on the same convention, and
there can be more than one consumer. Here, `Sparccall.ml`'s calling-
convention-specific return path (`Call.t.return`) and
`codegen/expander.ml`'s generic `GR.Return` CFG-node path
(`Mflow.machine.return`, wired from `Postexpander.S.return`) are two
*independent* return-emission sites for what looks like the same "return
from a function" construct - one had been given a target-specific,
correct implementation, the other was left as a generic architecture-
agnostic default (copied from another backend where the default happened
to also be correct) that silently did neither the delay-slot skip nor
the register-window `restore`. Grep for every place a Postexpander.S/
Mflow.machine field is *set*, not just where the "obvious" calling-
convention machinery lives, when a return/call-adjacent bug appears
target-specific but the target-specific-looking code all looks correct.


Tooling traps in this particular working copy
----------------------------------------------
- goken's Plan 9 versions of diff, sed, tail and cat come first on PATH.
  "diff -q" and "sed -i" both fail with confusing messages. Scripts here
  stick to plain "diff a b >/dev/null" and avoid sed -i. Bit the user
  directly once too: fork-tiger's own runtime/stdlib Makefiles use plain
  "sed 's/byteorder little/byteorder big/' src > $(B)/src" (no -i) to
  flip byteorder for ppc builds, and with goken9cc's bin ahead of GNU's on
  PATH this produced `make test-ppc` failures that looked like real qc--
  regressions - resolved by fixing PATH, not by touching any Makefile or
  source. `which sed` (and diff/tail/cat) is worth checking early whenever
  a ppc build/test failure doesn't match what a clean rebuild predicts.

- sort(1) collates by locale, so a recorded baseline's line order differs
  between a developer shell and a container. Force LC_ALL=C.

- pgrep -f "docker build ..." matches its own command line, so a wait-loop
  built on it never exits. Twice I reported a build as "still running" when
  it had already failed. Prefer waiting on the process you actually started.

- Wrapping a command as "cmd; echo EXIT=$?" makes the wrapper's exit status
  0, so an automated check sees success. Let the command be the last thing
  that runs.

- "cmd | grep -v pattern" reports grep's exit status, not cmd's - and grep -v
  exits 1 when every line matched the pattern (nothing left to print), which
  looks exactly like failure. Piping a real command through a warning filter
  and then checking "$?" reported a successful link as failed for several
  minutes. Check the underlying command's own exit status (a separate
  variable, or restructure so grep isn't last) instead of trusting $? after
  a filter pipe.

- /home/pad/github/fork-c-- and /home/pad/c-- are the *same* checkout
  (bind-mounted or equivalent - `stat -c '%i'` on the same file from both
  paths returns the same inode). A shell cd drifting to one instead of the
  other mid-session looks alarming ("did I just build/test the wrong
  repo?") but isn't - `git log`/`git status` from either path show
  identical state. Worth an inode check before assuming contamination,
  rather than redoing work out of caution.

- Backgrounding a long-lived process with "(cmd &)" then immediately
  checking on it in the *same* multi-line Bash call sometimes silently
  loses the process (no error, but `ps` finds nothing and log files are
  never created) - looked at first like a qemu/gdb-specific flakiness.
  Root cause was upstream of qemu: an earlier command in the same call
  returning nonzero (a `pkill` with nothing to kill, a `grep -v` with
  nothing left after filtering - see the trap above) combined with the
  harness's Bash tool aborting the rest of the script on the first
  nonzero exit status, so lines after it - including the backgrounding
  itself - simply never ran. Symptom was misleading because the *reported*
  failure was the last command in the block (gdb, or a `cat` of a file
  that consequently never got created), not the real culprit near the
  top. Fix: `cmd || true` on anything expected to sometimes legitimately
  return nonzero (pkill matching no process, grep matching nothing), or
  split suspect steps into separate tool calls so a silent abort is
  immediately visible instead of hiding inside a multi-line block.
